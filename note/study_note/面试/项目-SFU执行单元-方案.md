# 项目方案：可配置浮点与 SFU 执行单元

> **来源**：ChatGPT 对话，2026-10-29 导入（分享链接需登录，原文由用户粘贴）。
> **定位**：不是"写个浮点加法器、再用 LUT 算个 sin"的课程设计，而是一个**小型、可扩展的 GPU 数学执行单元**。
> **重点不是算子数量，是让面试官看到你理解计算单元的设计空间。**

## 一、定位

| 项 | 内容 |
|---|---|
| 名称 | Configurable Floating-Point & SFU Execution Unit |
| 方向 | RTL / 微架构 / 数值分析 |
| 核心思路 | 统一浮点数据通路 + 多格式支持 + 可配置 SFU 算法 + 性能与精度协同评估 |
| 一句话卖点 | 同一个执行单元里，既能谈浮点格式的共享与专用，也能谈近似算法的误差与成本，还能谈调度与吞吐 |

关键判断：**多格式不一定能完全共享同一套算术硬件**——"哪些逻辑能共享、哪些必须按格式配置"本身就是研究点，不要假装它能免费统一。

## 二、架构

```
统一指令接口（Ready/Valid · 操作路由 · 反压 · in-flight tracking）
        │
        ├─ Format Engine       FP32 / FP16 / BF16 / FP8
        │                      解码、规格化、舍入、异常值处理
        ├─ Arithmetic Pipeline  ADD / MUL / FMA
        │                      共享运算逻辑、流水线、结果打包
        ├─ SFU Pipeline        RCP / RSQRT / EXP2 / LOG2
        │                      范围规约、近似计算、结果重建
        └─ Verification        参考模型 / 误差 / PPA
```

> 这是**建议的项目架构**，不是某家 GPU 的内部实现复刻。多格式支持可参考 NVIDIA PTX 对 FP16/BF16/FP8 的区分，但不必一开始就实现全部格式。

## 三、三个设计点（项目的价值都在这里）

| 设计点 | 研究什么 | 对比维度 | 面试价值 |
|---|---|---|---|
| **A. 共享浮点数据通路** | FP32/FP16/BF16 哪些逻辑可共享，哪些必须按格式配置；参数化指数位宽与尾数位宽；统一解码、对齐、尾数运算、舍入的控制流 | 完全共享 / 部分共享 / 独立单元的面积与时序 | 能讨论微架构取舍，而不是复述浮点加法原理 |
| **B. 可配置近似 SFU** | 先做 RCP、RSQRT，再扩 EXP2/LOG2；比较 LUT、分段线性、分段多项式；范围规约、系数存储、FMA 求值、结果重建 | 不同精度目标下的最大误差、吞吐、硬件成本 | 能讨论数值算法怎么映射到真实硬件 |
| **C. 多执行单元调度** | FMA 与多周期 SFU 放进同一框架；长延迟 SFU 是否阻塞短延迟算术；共享 vs 独立 SFU 的资源竞争 | 混合指令比例下的吞吐、队列等待、背压 | 把已有的 cycle 级性能建模经验直接迁移过来 |

> SFU 的分段多项式方案有硬件研究基础：区间索引选多项式系数 → 乘法 + 融合累加完成近似求值。

## 四、三阶段交付（每阶段都有可展示结果）

| 阶段 | 实现内容 | 可展示的结果 |
|---|---|---|
| **第一阶段** | FP32 加法、乘法与 FMA；扩展 FP16/BF16 | 可综合 RTL、参考模型对拍、格式支持矩阵 |
| **第二阶段** | RCP、RSQRT；至少两种近似方案 | 误差分布、最坏误差、流水线延迟与吞吐对比 |
| **第三阶段** | 多操作调度、反压、cycle 级模型 | 混合指令负载下的性能分析与架构权衡 |

## 五、验证要求

**不要只看随机测试是否通过。**

| 类别 | 内容 |
|---|---|
| 定向测试 | NaN、Inf、非规格化数、±0、上溢、下溢、舍入边界 |
| 差分验证 | 正常数值计算 vs 高精度参考模型（Python / MPFR） |
| 误差报告 | 最坏误差、误差分布、ulp 统计 |
| 性能报告 | 延迟、吞吐、面积、关键路径 |

## 六、产出物清单

- [ ] 可综合的 SystemVerilog / Verilog RTL + 自动化测试框架
- [ ] Python 或其他高精度参考模型
- [ ] 不同浮点格式的误差与边界条件报告
- [ ] SFU 不同近似方案的精度、延迟、吞吐率比较
- [ ] 共享与专用数据通路的架构对比
- [ ] Cycle 级模型与混合负载性能分析

> 简历写法等有实测结果后再定：用数据描述支持的格式、函数、验证覆盖率、最大误差、性能差异，不写"实现了 SFU"这种没有数字的句子。

## 七、推荐切入点

```
多格式 FMA  →  RCP / RSQRT 的两种近似  →  统一调度框架
```

理由：这条路线同时有**数学深度**（近似算法与误差）、**RTL / 微架构深度**（共享数据通路与流水线）、**系统深度**（调度与性能建模），而且能复用已有的 GPU 性能建模经验。

## 八、不要做的事

- 不要一开始就实现 FP32/FP16/BF16/FP8 全部格式——先 FP32 FMA，跑通对拍再加格式。
- 不要堆算子数量——ADD/MUL/FMA 三个就够，深度在共享与配置。
- 不要只跑随机测试——NaN/Inf/denormal/舍入边界才是面试官会问的地方。
- 不要把"统一架构"说成免费的——共享的代价是时序和配置复杂度，要能给出对比数据。
