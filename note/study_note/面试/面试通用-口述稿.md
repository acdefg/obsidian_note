## 一、Memory 相关

### 1.1 常见的流控有哪些？

> **锚点**：三层框架 → TCP 窗口 → PCIe credit → memory 三件套 → 死锁
> **时长**：约 4 分钟（只留三层框架 + 各域一个代表，可压到 2 分钟）
> **术语**：watermark / PBFC（pause-based）· CBFC（credit-based）· token bucket · AIMD · PID · MPC

**一句话版**：先分三层——链路级逐跳反压（valid-ready / CBFC / PBFC 水线）、端到端接收窗口（TCP rwnd）、速率与拥塞控制（token bucket / AIMD / PID / MPC）。TCP 用后两层，PCIe 只有 CBFC，memory 三层都有。

#### 口述稿

TCP、PCIe、memory 里的“流控”其实不是同一层的东西，我一般先分三层再往里填。第一层是链路级、逐跳的反压，管下一跳有没有 buffer 接；第二层是端到端的接收窗口，管接收方还有没有空间；第三层是速率和拥塞控制，管发多快。三层可以叠加，不是互斥的。

TCP 只有后两层。它的流控就是接收窗口：每个 ACK 带一个 rwnd，发送方最多发到 `SND.UNA + rwnd` 这个右边界。窗口字段 16 位，原始上限 64 KB，长肥管道要靠 RFC 7323 的 window scaling，最大放到 1 GB。接收方 buffer 满了就通告零窗口，发送方用 persist timer 每 5 到 60 秒探一次，防止窗口更新丢了以后双方僵死；接收方还要做 SWS 规避，不能刚腾出几个字节就通告一个小窗口。这里要分清：rwnd 是流控，cwnd 是拥塞控制，实际窗口取两者最小值。AIMD、CUBIC、BBR 都是拥塞控制——AIMD 是加性增、乘性减，BBR 用带宽和最小 RTT 建模型，它们调的是 cwnd 和 pacing rate，不是 rwnd。

PCIe 只有链路级，而且是纯 CBFC，credit-based。它按 VC 记账，每个 VC 有六个池：Posted、Non-Posted、Completion 三类，每类再分 header 和 data。一个 header credit 是一个 TLP 头，一个 data credit 是 4 个 DW，也就是 16 字节。链路初始化用 InitFC1、InitFC2 交换额度，之后接收方每腾出空间就发 UpdateFC 归还。额度不够就发不出去，所以接收 buffer 不会溢出，也不用按 BDP 留 headroom。DLLP 自己不走流控；CRC 错了靠 DLL 层的 ACK/NAK 和 replay buffer 重传，那是可靠性，不是流控。PCIe 没有 pause 帧，也没有端到端窗口；completion credit 会让 requester 的 outstanding 有上限，但仍然是逐跳记账。

memory 系统三层都有。链路级最常见的是 AXI 的 valid/ready 握手（AXI 的通道和握手细节见 1.3），反压就是 READY 拉低，简单但没有信用记账；NoC 里一般升级成 per-VC credit，一个 VC 被堵住不影响别的 VC，这是消 HOL 的标准做法。到 memory controller 或 target 这一侧，常用水线：响应队列占用超过高水线就停发这个 VC 的读请求，低于低水线再放行，高低水线之间的间距就是滞回，防止抖动——这就是 PBFC 的思路，只是片上一般用 valid/ready 门控，不发 pause 帧。再往上是 outstanding 上限，也就是 inflight 数量，它相当于 memory 的接收窗口；按 Little's law，能撑住的带宽约等于 outstanding 乘每笔粒度再除以往返延迟。速率这一层，QoS 常用令牌桶：ARM 的 QoS-400 就是用 peak、burst、average 三个参数做 TSPEC 整形，再配 outstanding 上限和延迟反馈。PID、MPC 这类闭环控制理论上更优，但每拍要算、还要调参，RTL 里很少，更多出现在研究或者软件策略里。

横向比：credit 精确，但要记 buffer、还要占归还带宽；watermark 简单，但要留 headroom 和滞回；令牌桶是开环的，不知道下游堵不堵；AIMD 稳但收敛慢；PID 和 MPC 要模型、要调参。最后是死锁：credit 本身不会死锁，它只是没额度不发；真正的死锁是 buffer 或 VC 分配成环，解法是 escape VC 或者 turn model 把依赖图打断。

#### 追问预判

- **PCIe 为什么要分六个 credit 池？** 三类 TLP 的 buffer 不能互相占死：Completion 是对 Non-Posted 的响应，如果请求把 buffer 全占了，响应回不来，就会形成依赖环。分开记账保证每类都有前向进度。
- **PCIe 为什么不用 pause？** pause 要按 BDP 留 headroom，还要高低水线做滞回，长链路代价大；credit 精确到 buffer，且可以 per-VC 隔离。以太网用 PAUSE/PFC 是因为兼容性和实现成本。
- **TCP 流控和拥塞控制的区别？** rwnd 是接收方状态，cwnd 是网络状态；实际窗口取 `min(cwnd, rwnd)`。AIMD 属于后者。
- **watermark 和 credit 怎么选？** 短链路、小 FIFO、要极低延迟选水线；长链路、高带宽、要精确不浪费 buffer 选 credit。水线的隐藏成本是 headroom 和滞回。
- **memory 的 outstanding 上限怎么定？** 按 Little's law：`outstanding ≈ BW × 往返延迟 / 每笔粒度`。给小了打不满带宽，给大了排队延迟和 buffer 压力上来。
- **PID / MPC 为什么硬件里少见？** 每周期乘法、除法、求逆的代价高；参数要随工艺和负载重调；反馈延迟大时稳定性难保证。多数产品停在“水线 + credit + 令牌桶”。

### 1.2 NoC 和超节点的拓扑结构？

> **锚点**：直连 / 间接 → 四个指标 → 超节点 = scale-up 域 → 对分带宽
> **时长**：约 2.8 分钟

**一句话版**：直连看 mesh / torus，间接看 crossbar / fat-tree / butterfly / dragonfly；评价看直径、对分带宽、radix、平均跳数；超节点是 scale-up 域，内部是无阻塞 fat-tree 或全互联，关键指标是对分带宽和集合通信尾延迟。

#### 口述稿

拓扑我先按直连和间接分。直连是每个节点既是终端又是路由器，节点之间点对点连；间接是终端只挂在边缘，中间是纯交换网络。

直连里面最常见的是 mesh，二维或三维网格，布线规则、容易扩展，直径随节点数开方增长，对分带宽随规模线性涨，chiplet 和多核基本都从 mesh 起步。torus 是在 mesh 上加环绕连接，直径差不多减半，但那条长的环绕线物理上很难布，还要处理环绕方向的流控对称性，所以实际用得少。再往上是 cube 这类高维结构，维数越高直径越小，但每个路由器的端口数也越多。

间接网络里面，crossbar 是无阻塞的，但代价是 O(N²)，只在小规模成立——片上几十个 master 还行，上百个就不现实了。fat-tree 或者 Clos 是多级树，中间层加粗，对分带宽可以做到无阻塞，代价是交换级数和布线。butterfly 每一级的链路数是固定的，对分带宽受限，适合流量模式比较固定的场景。dragonfly 是层次化的，组内全连、组间全连，用非常少的全局链路换到很低的直径，是大规模超算的主流选择。

评价这些拓扑，我会看四个指标：直径、对分带宽、每个路由器的 radix，还有平均跳数。只说名字不说指标，其实等于没答。

然后是超节点。超节点本质是一个 scale-up 域：域内所有加速器共享一套高带宽、低延迟、支持内存语义的互连，可以直接互相访问显存；域外走 scale-out 网络，协议和延迟都差一个量级。所以超节点内部的拓扑一般不是 mesh，而是靠交换 ASIC 做的无阻塞 fat-tree 或者全互联——因为域内节点数可控，而集合通信比如 all-reduce、all-to-all 对无阻塞是刚需。它真正看的指标不是平均跳数，是对分带宽和集合通信的尾延迟。

再往外一层，多机多卡的时候常见的是 rail-optimized 的布线，同一张网卡编号的 GPU 接到同一台交换机，all-to-all 的流量就能均匀摊到各条 rail 上。这已经是拓扑和布线联合设计的问题了。

#### 追问预判

- **mesh 和 torus 的直径差多少？** k 元 n 维 mesh 直径 `n(k-1)`，torus 是 `n·⌊k/2⌋`；torus 约一半，但布线代价高。
- **超节点的瓶颈在哪？** 交换芯片的 radix、SerDes 的功耗和信号完整性、以及封装能引出多少高速 lane。
- **为什么 GPU 集群不用 dragonfly？** 收敛比和布线成本；GPU 侧的 all-to-all 对带宽敏感，超配比不能太低。

### 1.3 AXI 协议是什么？AXI Lite 和 AXI3、AXI4 有什么区别？

> **锚点**：五通道三件套 → 握手与 4KB → 三个成员 → AXI3→4 四点 → 落到项目
> **时长**：约 2.5 分钟

**一句话版**：AXI 是读写通道分离的内存映射总线，快在读写解耦、outstanding、ID 乱序；Lite 把突发整个删掉只剩单拍；AXI3→4 的关键是 256 拍、删写交织（W 必须跟 AW 顺序）、删 locked、加 QoS/Region。

#### 口述稿

AXI 是 ARM AMBA 里的高性能内存映射总线。它和 AHB 最大的区别是读写通道完全分开：写有 AW、W、B 三条通道，读有 AR、R 两条，一共五条。分开的好处是读写可以同时在途、互不阻塞，再配合 outstanding 和 ID 乱序，总线上能同时挂很多笔事务，带宽利用率才可能接近峰值。所以问 AXI 为什么快，答案不是「通道多」，而是读写解耦、多笔在途、乱序完成这三件套。

协议本身有一条握手规则要背死：VALID 一旦拉高必须保持到 READY，期间数据不能变，而且 VALID 不能组合依赖 READY，否则两端背靠背会形成组合环。地址上有两条硬约束：一笔 burst 不能跨 4KB 边界，因为 4KB 是页的粒度；WRAP 突发的长度只能是 2、4、8、16，起始地址还要按 size 对齐。

AXI4 这个家族有三个成员：Full、Lite 和 Stream。Lite 不是 Full 的性能降级版，它是把突发这个维度整个删掉了——没有 LEN、SIZE、BURST，每一笔就是单拍读写，数据宽度固定 32 或 64 位，也没有 ID，所以不能乱序。它存在的意义是寄存器配置本来就没有连续突发的语义，slave 可以做得非常小。Stream 是另一回事，它没有地址，只有数据流，用在视频、DSP 这类场景。

真正容易被追问的是 AXI3 到 AXI4 的差异，我记四点。第一，突发长度从最大 16 拍扩到 256 拍，目的是摊薄长 DMA 的命令开销，但仍然受 4KB 边界限制。第二，取消了写数据交织，WID 信号被删掉；代价是 AXI4 里 W 通道的数据必须严格按 AW 的顺序发，虽然不同 ID 的 B 响应仍然可以乱序。第三，删掉了 locked 传输，AxLOCK 从两位变成一位，只保留 exclusive，因为锁总线会让互连长时间被一个 master 占住，容易 HOL 甚至死锁。第四，新增了 QoS 和 Region，QoS 是给互连做仲裁的提示，Region 用来做地址区域译码。

落到我们 SoC 上，Crossbar 的仲裁输入就是 QoS 加轮询，乱序完成靠 ID 区分，DMA 的大块搬运就是靠长突发把命令开销摊薄。

#### 追问预判

- **outstanding 和交织有什么区别？** outstanding 是多笔事务同时在途，AXI3/4 都支持；交织是同一通道上不同事务的数据拍交替发送，只有 AXI3 的 W 通道支持，AXI4 删了。
- **AXI4 里两个不同 ID 的写，顺序规则是什么？** B 响应可以按 ID 乱序；W 数据不行，必须跟 AW 的顺序，因为已经没有 WID 了。
- **为什么 burst 不能跨 4KB？** 4KB 是 MMU 页粒度，跨页会让一笔 burst 落到两个物理页，地址译码和权限检查没法在发地址时一次确定。
- **AXI 是一致性协议吗？** 不是。AXI4 是 non-coherent 的，一致性要靠 ACE 在 AXI 上加 snoop 通道，或者直接上 CHI。
- **Lite 为什么不需要 ID？** 没有突发、没有乱序需求，而且配置寄存器天然要求全序，删掉 ID 能省掉响应重排逻辑。

## 二、AI 相关

### 2.1 你用 AI Agent 的心得？

> **锚点**：分两块 → 四层记忆 → 调试循环 → 分工与验证
> **时长**：约 3 分钟

**一句话版**：一块是养记忆——按更新频率分四层（公共背景 / 项目简介 / 任务详述 / 尝试与进度），答错先补上下文，同一个错犯两次就是 memory 没写好；另一块是干活——明确分工，没验证的代码不算产出。

#### 口述稿

我分两块讲。第一块是怎么养 agent 的记忆，第二块是怎么用它干活。

先说记忆。我的体会是，agent 的输出上限取决于它每次能读到的上下文，而 memory 不是写一次就好的配置，是像代码一样调试出来的。我按更新频率分四层：最底下是公共背景，放技术栈、术语、命名约定和禁止事项，这一层一个月改一次，跨项目通用；往上是项目简介，写这个项目做什么、模块怎么分、关键文件在哪，迭代级更新；再往上是任务详述，写当前这个 task 的目标、输入输出、约束、验收标准，还有哪些地方不要动，一个任务一份；最上面是尝试和进度，记试过什么、为什么失败、现在卡在哪。这一层可以让 AI 辅助记录，但一定要人审核，因为 AI 写的进度天然倾向写已完成，容易漏掉未验证，这两个差别是致命的。

分层的理由是上下文窗口有限，而且越具体的信息越有效。公共背景每轮都要，任务详述只在做那个任务时要，混在一起要么塞一堆无关内容稀释注意力，要么关键约束被淹没。

调试的循环是：agent 答错，先判断是缺上下文还是缺能力；如果缺上下文，就补到对应那一层，然后重跑同一个任务验证；如果同一个错犯了第二次，说明这条该升格，从任务级提到项目级甚至公共级。所以我的判断标准很简单：同一个任务上第二次犯同样的错，那不是模型问题，是 memory 没写好。

还有几条实操。写不要做什么，比写要做什么更值钱，约束比指令硬，也更省 token。进度日志一定要记失败的路，不然下一轮它会把排除过的方案再试一遍。memory 要定期删减，过时的项目简介比没有更糟，因为 agent 会当真。

第二块是用它干活。我的分工是：样板代码、API 查证、单测生成、日志分析、跨文件重构交给它；架构决策、性能模型的关键假设、要背锅的设计我自己做。验证上我的原则是没验证的代码不算产出，产出必须过编译、过单测，或者和 RTL、参考模型对齐。踩过的坑主要是两类：编造不存在的 API，和把一个小改动扩散成大面积重写，后者在性能模型里特别危险，因为它可能悄悄改掉关键假设。

#### 追问预判

- **举一个 memory 改进的具体例子？** 待补真实案例，最好带"改之前 / 改之后"的对比。
- **AI 写的代码你怎么 review？** 按风险分级：样板代码抽检，核心逻辑逐行，性能模型必须对齐参考数据。
- **会不会担心过度依赖？** 关键判断自己做，agent 负责扩大搜索面和执行速度。

## 三、编程建模相关

### 3.1 cycle 级建模的性能问题？

> **锚点**：两层成本 → 数量级 → 五个档位 → 活动稀疏度
> **时长**：约 2.7 分钟

**一句话版**：慢在"时间被切成固定步长"——空闲周期也全额付费。10⁸ 周期 × 1 μs ≈ 100 s；换成 40 周期一事件只要 2.5 s。加速谱系：event → 采样 → 区间 → trace → 解析。

#### 口述稿

会慢，而且慢的根源不是算得不准，是时间被切成了固定步长。我一般分两层说。

第一层是时间步长。cycle 级的时间以一拍为最小单位往前走，哪怕这一拍整个模型什么都没发生，也要走一遍求值。第二层是每步的求值范围，每个周期要把模型里所有模块扫一遍、重算所有状态。第一层是算法级的，第二层是实现级的；大多数人只讲第二层，说我优化了数据结构，但数量级差异其实来自第一层。

可以算个量级：假设一个 kernel 跑一亿个周期，这在 GPU 上就是几毫秒的量级。如果模型每个周期花一微秒，一亿个周期就是一百秒。换成事件驱动，如果平均四十个周期才有一个状态变化，事件数就是两百五十万个，还是每事件一微秒，总共二点五秒。四十倍的差距，来源不是模型变聪明了，是跳过了三十九比四十的空闲时间。

再往上还有几档加速，按丢掉的保真度排：第一档是换时间推进方式，也就是事件驱动，不丢精度，只是不逐拍求值，前提是活动稀疏。第二档是采样或者快进，只详细跑有代表性的区间，丢掉的是区间之间的长程耦合，比如热起来之后的稳态。第三档是区间模拟，不逐周期算 stall，用解析式估一段指令流的停顿，误差集中在单次事件的确切周期数上。第四档是 trace-driven，前端跑一次生成访存 trace，后端只重放存储系统，丢掉的是执行和访存的时序耦合——trace 里的地址是没被阻塞时才会出现的序列，一旦存储真堵了，真实程序会改变访存节奏，trace 不会。最后一档是纯解析模型或者 roofline，只算上界。

有一个点要注意：报加速比必须说清 baseline，是相对 RTL 仿真、相对另一个 cycle 模型，还是相对 trace 模型。快一百倍不说 baseline 等于没说。

#### 追问预判

- **事件驱动一定更快吗？** 不一定，活动密集时更慢——见 3.3。
- **模型准不准怎么验证？** 对齐 RTL 或硬件 counter，看误差的分布而不是均值。
- **采样会不会漏掉尾延迟？** 会。尾延迟本身是低频事件，采样容易采不到，要专门设计触发条件。

### 3.2 TLM 是什么？1.0 和 2.0 有什么区别？

> **锚点**：事务级 → 消息 vs 内存映射 → 三件套 → DMI / quantum
> **时长**：约 3 分钟

**一句话版**：TLM 用一次事务代替引脚电平，价值是能早点跑、跑得动。1.0 是消息传递，2.0 是内存映射总线，两者不兼容、并存。2.0 三件套 = 接口（LT/AT）+ socket + generic payload；提速靠 DMI 和 quantum。

#### 口述稿

TLM 是事务级建模。它用一次数据交换来描述通信，而不是引脚上的电平变化。一次事务可以是一个字的读、一个 burst，甚至一整帧。它的价值不是仿真更准，而是把不需要的细节抽象掉之后能跑得动、能早点跑——比如 RTL 还没有的时候软件就能开发，或者架构探索阶段粗估带宽和延迟。

TLM 不是一个精度，是一个抽象层区间，从无时序的函数调用到带近似时序的流水建模都算。

TLM 1.0 和 2.0 不是版本升级，是两种风格。1.0 是消息传递，核心接口是 `tlm_transport_if` 的 transport，配合 `tlm_fifo` 做 put/get，数据类型是用户自己定义的模板。2.0 是内存映射总线，用的是通用 payload，地址、命令、数据、响应这些字段是标准化的。两者在 IEEE 1666 里并存，但互相不兼容。

2.0 我一般讲三件套。第一是接口，分阻塞和非阻塞：loosely-timed 用 `b_transport`，调用即完成，延迟是通过引用沿途累加的；approximately-timed 用 `nb_transport_fw` 和 `nb_transport_bw`，立即返回一个同步枚举，用 phase 多次往返。phase 的标准四段是 BEGIN_REQ、END_REQ、BEGIN_RESP、END_RESP，中间允许省略。第二是 socket，initiator 和 target，绑一次就把前向、后向和 DMI 三个接口都接上了。第三是 generic payload，地址、命令、数据长度、byte enable、response 这些字段固定，扩展靠 `tlm_extension` 挂自定义字段，比如 QoS 或者 cache 属性。

提速上有两个关键。一个是 DMI，target 告诉 initiator 这块地址我给你裸指针，之后直接读写，不用每笔都走 socket 调用和 payload 构造；映射变了要回调 invalidate 通知 initiator。另一个是 temporal decoupling，配 quantum keeper，每个 initiator 有本地时间，允许领先全局时间一个 quantum，越过边界才真正 sync。quantum 越大越快，但时间精度越差，所以不能超过你关心的最小时间粒度。

最后落到项目上：我的 cosim 里 TLM 只用来做参考模型和激励注入，事务边界必须能一一映射到 RTL 的采样点，否则 scoreboard 对不上；真正的时序还是 cycle 级模型算的。

#### 追问预判

- **LT 和 AT 怎么选？** 只要功能 + 粗性能选 LT；需要表达流水、反压、乱序选 AT。
- **什么时候不能给 DMI？** 访问有副作用、需要记统计、地址映射会动态变的时候。
- **为什么 2.0 不兼容 1.0？** 数据模型不同——1.0 是任意用户类型，2.0 是固定字段的 generic payload。

### 3.3 事件驱动建模是怎么回事？

> **锚点**：事件队列 → 跳空闲 → delta cycle → 活动稀疏度
> **时长**：约 2.5 分钟

**一句话版**：所有状态变化变成带时间戳的事件，时间从一个事件跳到下一个，空闲周期零成本。它不是更准也不是更不准，快慢取决于活动稀疏度；delta cycle 处理同一时刻的多次求值。

#### 口述稿

事件驱动的核心是事件队列。所有状态变化都表示成一个带时间戳的事件，插进有序队列；调度器每次取最早的那个，把时间推到它的时刻。和 cycle 级最根本的区别是时间不按固定步长前进，而是从一个事件跳到下一个事件，所以空闲周期是零成本的——这是它快的来源。

但要说清一点：事件驱动不是精度更高或者更低，它是同一种精度换一种时间表示。如果你把每个时钟沿都建成事件，它的精度和 cycle 级完全一样，速度也一样慢。所以真正的判据是活动稀疏度，也就是平均多少个周期才发生一次状态变化。GPU 的存储子系统就很稀疏，一个 warp 几十上百个周期才发一次请求，L2 和 HBM 在两次请求之间根本不变，这种结构天生适合事件推进。反过来，满负荷的流水线或者每拍都在变的计数器，事件密度接近每周期一个，每个事件还要付入队、排序、出队的开销，可能比 cycle 级顺序扫一遍数组还慢。

实现上有几个坑。delta cycle 是同一时刻需要多次求值才能稳定的情况，比如组合逻辑链或者零延迟事务，SystemC 里 `wait(SC_ZERO_TIME)` 就是进下一个 delta，不推进时间。另一个坑是同一时刻的事件顺序不确定会导致仿真不可复现，解决办法是给同一时刻的事件定优先级。

工具上，gem5 就是事件驱动的典型，核心是 EventQueue 加 SimObject 加 Port，扩展点主要是 schedule 和 deschedule。SystemC 也是事件驱动，只是它的调度器多了一个 evaluate 和 update 的分离，signal 的写要到 update phase 才可见，这一点和 Verilog 的非阻塞赋值是一样的。

#### 追问预判

- **delta cycle 会不会死循环？** 会，组合环就是典型；和 Verilog 一样要靠设计约束。
- **事件驱动怎么并行？** 保守 PDES 需要 lookahead，乐观 PDES（Time Warp）要回滚，代价都不低。
- **gem5 里怎么加一个新模块？** 继承 SimObject，声明参数和端口，在构造函数里 schedule 首个事件。

### 4.2 项目：异步通信 DMA（摩尔线程）

> **锚点**：背景 → 我的职责 → 三个设计 → 量化 → 一个 trade-off
> **时长**：约 2.5 分钟

**结构**：先讲**问题**（为什么原来的方案不够），再讲**你做了什么**，最后讲**结果和一个取舍**。不要一上来讲模块框图。

#### 口述稿（模板）

这个项目是给 C2C 和 D2D 做一套可配置的异步数据搬运引擎。背景是⚠️【待填：原来的搬运路径哪里不够——是带宽利用率低、延迟高，还是跨卡流量会挤掉本地流量】。

我负责的是⚠️【待填：调度器 / 流控 / 完成通知中的哪一块】。

关键设计有三个。第一，⚠️【HOL 的成因：是共享队列、共享虚拟通道还是共享 credit】；我们的做法是⚠️【隔离手段】。第二，流控用的是 credit-based，credit 粒度按⚠️【flit / 包 / 事务】定，额度不足时反压到⚠️【上游模块还是软件】。第三，unbalance 的处理是⚠️【静态配置还是动态统计，窗口多大】。

结果是跨卡传输性能做到 **3×**，流量竞争消除 **90%**。基线是⚠️【待填：什么配置、什么 pattern、是否含竞争场景】，测试覆盖了⚠️【待填】。
