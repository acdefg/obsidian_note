## 1. 流控（没答上来）

### 复盘要点

面试官问的是「**常见**的流控」，要的是**分类**，不是项目细节。我当时的回答陷在 credit-based 里出不来——那是**链路级**的一种，只占整张图的一格。

### 答题骨架（下次按这个顺序讲）

> 2026-10-25 更新：按 **TCP / PCIe / memory** 三个域重新整理的三层版见 [[面试通用-口述稿#1.1 常见的流控有哪些？]]。下面四层骨架保留作**链路级细节**；面试先讲三层框架，再落到各域一个代表。

**第一层：分链路级和端到端。**

- **链路级**：管的是「下一跳有没有 buffer」。不关心端到端是否送达。
- **端到端**：管的是「接收方应用/协议栈有没有空间」，典型是滑动窗口、TCP 拥塞控制。
- **两者叠加**：以太网就是链路层 PAUSE + 传输层滑动窗口同时存在。

**第二层：链路级的四种做法。**

| 机制 | 怎么反压 | 代价 | 典型场景 |
|---|---|---|---|
| ready/valid 握手 | 反向 ready 线，组合逻辑直接拉低 | 长距离反压线延迟大、组合环风险 | 片内短距离、AXI |
| credit-based | 发送方扣 credit，接收方腾出 buffer 才归还 | 需要预先知道对端 buffer 深度；归还路径本身要点带宽 | 片内 NoC、PCIe、跨卡链路 |
| ACK/NACK + 重传 | 收到 ACK 才释放，丢了重发 | 延迟高、需要重传 buffer | 有误码的串行链路（PCIe 链路层、以太网） |
| pause 帧 / 定时停等 | 显式发暂停帧 | 粒度粗、反应慢 | 以太网 |

**第三层：NoC 里的两个特化。**

- **按 flit 计 credit**：wormhole 交换不整包缓冲，credit 单位从「包」变成「flit」，buffer 深度按 flit 算。
- **per-VC credit**：每条虚拟通道独立 credit。一个包被下游挡住时，只堵它自己那条 VC，其它 VC 继续走——这是消除 **HOL 阻塞**的手段。注意：HOL 在**队列/VC 粒度**上被消除，在**物理链路**粒度上仍然存在。

**第四层：credit 会不会死锁。**

- credit 机制**本身**不产生死锁：它只是"没额度就不发"，不会持有一个资源去等另一个。
- 真正的死锁来自 **buffer 分配成环**：A 等 B 的 buffer、B 等 C、C 等 A。环上每个节点都占着自己的输入 buffer 不放。
- 解法是打破环：**escape VC**（留一条走固定路由的通道）、**turn model**（禁止某些转向，让依赖图无环）、或**严格的 VC 分配顺序**。

## 2. NoC 与超节点拓扑（没答上来）

### 复盘要点

同样是「要词表」的问题。拓扑题的标准答法是**先按直连/间接分，再逐个报指标**：直径、对分带宽、radix（每个路由器的端口数）、平均跳数、代价。只说名字不说指标，等于没答。

### 答题骨架

**第一层：直连 vs 间接。**

- **直连（direct）**：每个节点既是终端又是路由器，节点间点对点连。
  - **mesh**：2D/3D 网格。直径 ∝ √N，对分带宽随规模线性增长。布线规则、易扩展，是 chiplet / 多核最常见的起点。
  - **torus**：mesh 加环绕连接。直径减半，但**长环绕线**在物理上难布，且需要处理环绕的流控对称性。
  - **cube / 高维**：维数越高直径越小、每节点端口越多。
- **间接（indirect）**：终端只连边缘，中间是纯交换网络。
  - **crossbar**：无阻塞但代价 O(N²)，只在**小规模**（片上几十个 master）成立。
  - **fat-tree / Clos**：多级树，中间层加粗。对分带宽可做到无阻塞，代价是交换级数和布线。
  - **butterfly**：每级链路数固定，对分带宽受限，适合固定流量模式。
  - **dragonfly**：层次化——组内全连、组间全连。用极少的全局链路换低直径，是**大规模超算**的主流选择。

**第二层：超节点是什么。**

- 定义：一个 **scale-up 域**——域内所有加速器共享一套高带宽、低延迟、支持内存语义的互连，可以互相直接访问显存；域外走 scale-out 网络（以太网 / InfiniBand），协议和延迟都差一个量级。
- 拓扑上，超节点内部通常是**通过交换 ASIC 做的无阻塞 fat-tree 或全互联**，不是 mesh——因为域内节点数可控（几个到几十个），而无阻塞对集合通信（all-reduce / all-to-all）是刚需。
- 关键指标不是"平均跳数"，而是**对分带宽**和**集合通信的尾延迟**——超节点的存在意义就是让 all-to-all 不经过 scale-out 网络。

**第三层：为什么 GPU 集群是 rail-optimized。**

- scale-out 侧多机多卡时，同一张网卡编号的 GPU 接到同一台交换机（一条 rail）。all-to-all 时流量均匀分摊到各 rail，避免单条上行拥塞。这属于**拓扑 + 布线**的联合设计，不是纯网络问题。

> ⚠️ 具体端口数 / 带宽数字（NVSwitch 端口数、NVLink 每代速率、UALink 规格）**待核**，本场没答上来时不要现编。定性讲清「无阻塞 / 对分带宽 / 层次化」比报错数字强。

## 3. cycle 级建模 / TLM / 事件驱动（待自评）

> 这三题当场问了，但没标「没答上来」。**先回放录音或回忆原话再填**，不要凭印象给自己打高分。

### 3.1 cycle 级建模的性能问题（会不会跑得很慢）

**一句话回答**：会，而且慢的原因不是"算得不准"，而是**时间被切成了固定步长**——即使这一拍整个模型什么都没发生，也要走一遍求值。所以 Cycle 级建模的核心工程矛盾是：**精度来自逐拍推进，成本也来自逐拍推进**。

#### 慢在哪一层

慢有两层，面试时要说清是哪一层：

| 层次 | 成本来源 | 缓解手段 |
|---|---|---|
| **① 时间步长** | 时间以 1 cycle 为最小单位前进，空闲周期也占满额成本 | 换成事件推进（见 §3.2） |
| **② 每步求值范围** | 每个周期都要遍历模型里所有模块、重算所有状态 | 惰性求值、只更新活跃模块 |

第一层是**算法级**的，第二层是**实现级**的。很多人只讲第二层（"我优化了数据结构"），其实第一层才是数量级差异的来源。

#### 数量级：一个能自己验算的例子

设一个 kernel 跑 10⁸ 个周期（GPU 上一个几毫秒的 kernel 就是这个量级，1.5 GHz × 66 ms ≈ 10⁸）。

| 模型 | 每单位时间成本 | 单位数 | 总时间 |
|---|---|---|---|
| cycle-based，每周期 1 μs | 1 μs | 10⁸ 个周期 | **100 s** |
| event-driven，平均 40 周期一个事件 | 1 μs | 2.5×10⁶ 个事件 | **2.5 s** |

**40× 就是这么来的**——不是模型变聪明了，是**跳过了 39/40 的空闲时间**。这个 40× 完全由「活动稀疏度」决定，跟精度无关。

#### 五个加速档位（按丢掉的保真度排序）

1. **换时间推进方式**（event-driven）：不丢精度，只丢"每拍求值"这个习惯。前提是活动稀疏。
2. **采样 / 快进**（SMARTS 式）：只详细跑有代表性的区间，其余快速跳过或解析估算。丢掉的是**区间之间的长程耦合**（比如热起来之后的稳态行为）。
3. **区间模拟（interval simulation）**：不逐周期算 stall，用解析式估算一段指令流的停顿。误差集中在**单次事件的确切周期数**，瓶颈归因通常还对。
4. **trace-driven**：前端跑一次生成访存 trace，后端只重放存储系统。丢掉的是**执行与访存的时序耦合**——trace 里的地址序列是"没被阻塞时才会出现"的序列，一旦存储真的堵了，真实程序会改变访存节奏，trace 不会。这是必答的取舍。
5. **分析模型 / roofline**：完全不模拟，只算上界。

> ⚠️ 报加速比必须说清 baseline：是相对 RTL 仿真、相对另一个 cycle 模型、还是相对 trace 模型？「快 100×」不说 baseline 等于没说。

### 3.2 事件驱动 vs cycle 级：对比

**先纠正一个常见误解**：这两者**不是精度高低的关系**，是**时间怎么表示**的关系。

- 一个 event-driven 模型，如果把每个时钟沿都建模成一个事件，它的精度和 cycle-based **完全一样**，速度也**一样慢**。
- 一个 cycle-based 模型，如果每周期只更新变化了的模块，它也能变快，但**永远跳不过空闲周期**。

所以真正的区别是：**时间轴是"离散的点"还是"等距的刻度"**。

#### 对比表

| | **cycle-based（固定步长）** | **event-driven（离散事件）** |
|---|---|---|
| 时间怎么前进 | 每周期 `t += 1` | 从事件队列取最早事件，`t = event.time` |
| 空闲周期 | 全额付成本 | **零成本** |
| 精度 | 逐拍精确 | 可做到逐拍精确（取决于事件粒度） |
| 速度决定因素 | 周期数 × 每周期求值量 | **事件密度** × 每事件处理成本 |
| 每事件额外开销 | 无（顺序遍历） | 有：入队/出队的排序成本 |
| 并行化 | 同周期内模块相对独立，可用保守 PDES | 事件有因果依赖，要乐观 PDES（Time Warp） |
| 典型代表 | 自研 Cmodel、Verilator（2-state） | gem5、SystemC、GPGPU-Sim 的部分子系统 |

#### 什么时候 event-driven 更快，什么时候反而更慢

判据只有一个：**活动稀疏度** = 平均多少个周期才发生一次状态变化。

- **稀疏**（几十到几百周期一个事件）→ event-driven 大赢。
  GPU 存储子系统是典型：一个 warp 每几十上百周期才发一次请求，L2/HBM 的状态在两次请求之间根本不变。这种结构天生适合事件推进。
- **密集**（每周期 1 个以上事件）→ event-driven **可能更慢**。
  满负荷的流水线、每个周期的时钟沿本身、每拍都在变的计数器——每件事都要入队、排序、出队，比直接顺序扫一遍数组还贵。

一个能验算的反例：同样 10⁸ 周期，若事件密度是每周期 1.2 个 → 1.2×10⁸ 个事件，每事件除 1 μs 还要付排序开销（假设 +30%）→ **156 s，比 cycle-based 的 100 s 更慢**。

#### 怎么在面试里把这三题串起来

面试官问「cycle 级建模的性能问题」→ 你答「慢，因为固定步长」→ 他顺势问「那事件驱动呢」→ 你答「事件驱动是同精度的另一种时间表示，快在跳过空闲，慢在事件密集时」→ 他再问「TLM 呢」→ 你答「TLM 是**再往上一档**，连事务内部的拍数都不建了」→ 落回项目：「所以 cosim 必须 cycle 级（要和 RTL 逐拍对齐），Cmodel 做设计空间探索用 TLM/trace 就够」。

这条链走完，说明你脑子里有**精度—速度谱系**，而不是三个孤立的名词。

### 3.3 TLM（问的是"这些接口你熟不熟"）

> 这题的失分点不在概念，在**接口名**。面试官问「TLM 相关问题」，实际在探：你知不知道 `b_transport` / `nb_transport_fw`、知不知道 socket 和 payload、写过还是只听过。下面按「是什么 → 1.0 和 2.0 分家 → 2.0 的三件套 → 提速手段 → SystemC 本身」组织，可以直接背。

#### ① TLM 是什么

**TLM = Transaction Level Modeling，事务级建模。** 用「一次数据交换」（transaction）而不是「引脚上的电平变化」来描述通信。一次事务可以是一个字的读、一个 burst、甚至一整帧。

它的价值不在"仿真更准"，而在**抽象掉不需要的细节后能跑得动、能早点跑**：

- 软件在 RTL 还不存在时就能开发（虚拟平台 / virtual prototype）
- 架构探索阶段粗估带宽、延迟、吞吐
- 验证平台里当参考模型，给 scoreboard 提供激励接口

一句话定位：**TLM 不是一种精度，而是一个抽象层区间**——从"无时序的函数调用"到"带近似时序的流水建模"，都算 TLM。

#### ② TLM-1.0 和 TLM-2.0 是两种风格，不是版本升级

这是最能区分"听过"和"用过"的一问。

| | **TLM-1.0** | **TLM-2.0** |
|---|---|---|
| 定位 | **消息传递**（message passing） | **内存映射总线**（memory-mapped bus） |
| 核心接口 | `tlm_transport_if<REQ,RSP>` → `transport()`；`tlm_fifo` + `put/get/peek` | `b_transport()`（阻塞）、`nb_transport_fw()/nb_transport_bw()`（非阻塞）、`get_direct_mem_ptr()` |
| 数据类型 | 用户自定义模板类型 | **标准 generic payload**（地址/命令/数据/响应等字段固定） |
| 时序表达 | 基本不建 | 用 **phase** 表达（BEGIN_REQ / END_REQ / BEGIN_RESP / END_RESP） |
| 互操作性 | 各家自定义类型，难互通 | 协议和 payload 标准化，可互操作 |
| 典型场景 | 抽象算法模型、消息通道 | SoC 总线建模、架构性能分析、虚拟平台 |

**要点**：TLM-2.0 **不兼容** TLM-1.0，两者在 IEEE 1666 里**并存**。TLM-1.0 适合"两个模块传消息"，TLM-2.0 适合"模拟一根总线上的读写"。面试时能说清这条分界线，比背接口名更有说服力。

#### ③ TLM-2.0 的三件套

**接口（interface）—— 按时序精度分两种**

| 模式 | 接口 | 语义 | 用途 |
|---|---|---|---|
| **LT**（loosely-timed） | `b_transport(payload, delay)` | 调用即完成，`delay` 是**引用**，沿途累加延迟 | 软件开发、系统级初探 |
| **AT**（approximately-timed） | `nb_transport_fw(payload, phase, delay)` / `nb_transport_bw(...)` | 立即返回 `tlm_sync_enum`，用 phase 多次往返 | 架构探索、需要表达流水和反压 |

`tlm_sync_enum` 三个值：`TLM_ACCEPTED`（收下，稍后回）、`TLM_UPDATED`（收下且 phase 变了）、`TLM_COMPLETED`（事务结束）。

**socket —— 接口的绑定封装**

- `tlm_initiator_socket`（发起方）/ `tlm_target_socket`（响应方）
- 常用的是 `tlm_utils::simple_initiator_socket` / `simple_target_socket`，以及支持多 target 的 `multi_passthrough_target_socket`
- socket 内部绑定了**多个接口**（fw + bw + dmi），所以绑一次 socket 就把三个方向都接上了

**generic payload —— 标准事务包**

`tlm_generic_payload` 的必备字段：

- `m_address` / `m_command`（`TLM_READ_COMMAND`、`TLM_WRITE_COMMAND`）
- `m_data` / `m_data_length` / `m_byte_enable`
- `m_response`（`TLM_OK_RESPONSE`、`TLM_INCOMPLETE_RESPONSE`、`TLM_GENERIC_ERROR_RESPONSE` 等）
- `m_dmi`（是否允许 DMI）/ `m_gp_option`
- **扩展机制**：`tlm_extension<T>` 可以挂自定义字段（QoS、cache 属性、安全标签）。这是 TLM-2.0 能表达"标准字段之外的协议信息"的关键。

**AT 的 phase 流程**（base protocol，四段）

1. initiator → target：`BEGIN_REQ`
2. target 收下后 → initiator：`END_REQ`（表示请求已接收，可以释放请求 buffer）
3. target → initiator：`BEGIN_RESP`
4. initiator 收下后 → target：`END_RESP`

简化协议（`BEGIN_REQ` 直接跳 `BEGIN_RESP`）也合法——面试时说"允许省略中间 phase"是加分项。

#### ④ 两个提速关键：DMI 和 temporal decoupling

**DMI（Direct Memory Interface）**

- 问题：LT 模式下每笔事务都要走一次 socket 调用 + payload 构造，即使只是读同一个 RAM。
- 做法：target 通过 `get_direct_mem_ptr()` 告诉 initiator「这段地址范围我给你一个**裸指针**，之后直接读写，不用再调我」。
- `tlm_dmi` 里带：地址范围（start/end）、指针、granted access（`DMI_ACCESS_READ` / `WRITE` / `READ_WRITE`）、read/write latency。
- 失效：映射变了要回调 `invalidate_dmi_ptr()`，否则 initiator 拿的是野指针。
- **收益是数量级的**：省掉每笔事务的虚函数调用和 payload 构造。

**temporal decoupling + quantum**

- 问题：LT 下如果每笔事务都和全局时间同步，上下文切换成本吃掉所有收益。
- 做法：`tlm_utils::tlm_quantumkeeper`，给每个 initiator 一个**本地时间**，允许领先全局时间最多一个 `global quantum`。只有越过 quantum 边界才 `sync()`（真正 `wait`）。
- 效果：一次 `wait` 覆盖多笔事务，切换次数按 quantum 缩小。
- **取舍**：quantum 越大越快，但**时间精度越差**——模型可能"看见"未来一个 quantum 内才发生的事。所以 quantum 不能超过你关心的最小时间粒度。

#### ⑤ SystemC 本身的特性（被追问时会用到）

**层次结构**：`sc_module` 可嵌套，`SC_MODULE` 是宏糖；模块间通过 port / export / socket 连接，不是全局变量。

**三种进程**（这是必答对比）：

| 进程类型 | 能否 `wait()` | 敏感方式 | 用途 |
|---|---|---|---|
| `SC_METHOD` | **不能** | 静态敏感列表 / `next_trigger()` | 组合逻辑、寄存器更新；不消耗时间 |
| `SC_THREAD` | **能** | 动态 `wait(event/time)` | 行为建模、激励生成、TLM initiator |
| `SC_CTHREAD` | 能（只能等时钟沿） | 固定为时钟边沿 | 可综合子集，RTL 风格 |

**通信原语**：`sc_signal`、`sc_fifo`、`sc_mutex`、`sc_semaphore`、`sc_event`、`sc_event_queue`。

**调度语义**（和 Verilog 的相似性，讲出来很显功底）：

```
initialize → evaluate（跑所有就绪进程）→ update（提交 signal 新值）
           → 有 delta 事件？→ 回到 evaluate
           → 没有 → 推进到下一个时间点
```

- `sc_signal::write()` **不是立即生效**，要到 update phase 才可见 → 等价于 Verilog 的**非阻塞赋值**。
- 同一时刻的多次更新靠 **delta cycle** 收敛，所以组合环会死循环（和 Verilog 一样）。
- `wait(SC_ZERO_TIME)` = 进下一个 delta，不推进时间。

**关键卖点**：SystemC **同一个语言覆盖多个抽象层**——用 `sc_signal` + `SC_METHOD` 可以写逐拍 RTL 风格模型，用 TLM socket 可以写事务模型，两者能在同一个仿真里混用。这是它相对"纯 C++ 自研建模框架"的最大优势。

#### ⑥ 落回项目（一定要接这一句）

> "我的 cosim 里 TLM 部分只用来做**参考模型**和**激励注入**：TLM 事务边界必须能一一映射到 RTL 的采样点，否则 scoreboard 对不上。真正的时序还是靠 cycle 级模型算的。"

这句话把 TLM（抽象层）和 cycle 级（精度）两个轴同时摆出来了。

### 3.4 事件驱动的实现细节

时间推进方式和 cycle 级的对比已在 §3.2 讲过，这里只留实现层要答的点：

- 核心是**事件队列**：所有状态变化都表示成 `(time, event)` 插入有序队列，调度器每次取最早的事件推进时间。
- **delta cycle**：同一时刻需要多次求值才能稳定的情况（组合逻辑链、零延迟事务）。SystemC 的 `wait(SC_ZERO_TIME)` 就是进下一个 delta。
- 必答的坑：事件顺序在同一时刻不确定 → 仿真不可复现；解决办法是给同一时刻的事件定优先级。
- gem5 的对应物：EventQueue + SimObject + Port；`schedule()` / `deschedule()` 是扩展点。

## 4. AI Agent 使用心得（非技术题）

### 复盘要点

这题考的是**工程判断**，不是工具熟练度。答成「我常用 Claude Code / Cursor 帮我写代码」是零分——面试官想知道的是：你怎么分工、怎么验证、什么时候不信它。

### 答题骨架：分两部分

> 面试官问「心得」，要的是**方法论**，不是工具清单。我的回答分两块：① **怎么养 agent 的记忆**（上下文工程）；② **怎么用它干活**（待补，见文末）。

#### 第一部分：AI 公共 memory 的调试

**核心观点**：agent 的输出上限，取决于它每次能读到的上下文。memory 不是"写一次就好"的配置，而是**像代码一样调试出来的**——它答错了，先问"是不是我少给了它什么"，再问"是不是它能力不够"。

**四层结构**

| 层 | 写什么 | 更新频率 | 谁维护 | 什么时候失效 |
|---|---|---|---|---|
| **① 公共背景** | 技术栈、术语表、命名/编码约定、常用命令、**禁止事项** | 低（周/月） | 人 | 跨项目通用，长期稳定 |
| **② 项目简介** | 这个项目做什么、模块怎么分、关键文件在哪、上下游是谁 | 中（迭代级） | 人写 + AI 起草 | 项目演进后就过时 |
| **③ 任务详述** | 当前 task 的目标、输入输出、约束、验收标准、**不要动的地方** | 每任务 | 人 | 任务结束即废弃 |
| **④ 尝试与进度** | 试过什么、为什么失败、当前卡在哪、下一步 | 每轮 | **AI 辅助记录，人审核** | 任务结束归档 |

**为什么必须分层**：上下文窗口有限，而且**越具体的信息越有效**。公共背景每次都要，任务详述只在做那个任务时要——混在一起，要么每轮塞一堆无关内容稀释注意力，要么关键约束被淹没。

**调试循环**（"调试"两个字的落点）

```
agent 答错 → 判断是「缺上下文」还是「缺能力」
          → 缺上下文 → 补到对应层 → 重跑同一任务验证
          → 同一个错犯第二次 → 说明该「升格」：任务级 → 项目级 → 公共级
```

**四条实操经验**

1. **写「不要做什么」比写「要做什么」更值钱。** 约束比指令更硬，也更省 token——"不要改 `include/` 下的接口"一句话，能挡住一整类跑偏。
2. **进度日志一定要记失败的路。** 只记"做了什么"，agent 下一轮会把已经排除的方案再试一遍。
3. **让 AI 辅助记录，但人要审核。** AI 写的进度天然倾向写"已完成"，容易漏掉"未验证"——这两者差别是致命的。
4. **定期删减。** memory 只增不减，噪音会盖过重点；**过时的项目简介比没有更糟**，因为 agent 会当真。

**一个判断标准**：如果 agent 在同一个任务上第二次犯同样的错，那不是模型问题，是 **memory 没写好**。

#### 第二部分：怎么用它干活（待补）

> 这里需要你补一句：这一场实际讲的第二块是什么。以下是候选内容，确认后我删改：
>
