# CUDA 内存模型

## Pinned Memory 是什么？为什么是异步 DMA 的前提？ #cuda #memory #dma #pinned-memory

> **速查**
> - 页锁定（page-locked）主机内存：物理页在 DMA 期间不可换出、不可搬移
> - 价值：让 `cudaMemcpyAsync` 真正异步；pageable 源会**静默退化**为同步拷贝
> - 代价：分配昂贵（改页表 + 锁物理页）+ 占不可回收物理内存 → 工程上做 Pinned Pool
> - 「能安全提交异步 DMA」是**必要条件**，≠「传输一定被计算隐藏」

### 正文

**① 为什么分页内存做不了 DMA**

虚拟内存的页表允许 OS 随时换出 / 搬移页面。这对 CPU 是透明的（CPU 走 MMU，拿到的是虚拟地址），但对 GPU 的 DMA 引擎致命：DMA 直接按**物理地址**搬数据，若传输途中页面被换出或搬走，数据就会损坏。

所以 pageable（普通 `malloc`）内存不能直接交给 DMA 引擎 —— 这是问题的根，不是性能问题。

**② 两条拷贝路径**

| | Pageable（`malloc`） | Pinned（`cudaMallocHost` / `cudaHostAlloc`） |
|---|---|---|
| 物理页 | 可换出 / 可搬移 | 锁定、地址稳定 |
| 拷贝路径 | 驱动先拷到内部 staging buffer，再 DMA | 直接 DMA |
| `cudaMemcpyAsync` | **必然阻塞**（退化成同步） | 立即返回、真正异步 |
| 分配 | 便宜 | 昂贵（改页表 + 锁物理页） |

关键：pageable 源之所以不报错却没有异步效果，正是因为驱动在背后替你做了「拷进 staging buffer」这一步，而这一步是同步的。

**③ 必要条件 ≠ 充分条件**

教材截图那句：「它解决『能否安全提交异步 DMA』的条件问题，并不保证传输一定被计算隐藏。」

- pinned 保证的是**能安全地**把 DMA 交给异步引擎（地址在整个传输期间稳定）——这是**前提条件**。
- 「能异步」≠「被隐藏」：异步提交只是把传输排进了 stream 队列，是否真正与计算重叠，还取决于 stream 编排、依赖顺序、以及计算是否足够久到盖住传输时间。

**④ 代价与工程取舍**

- 分配慢：需要改页表 + 锁物理页。
- 占不可回收物理内存，**过量会拖慢整个系统**（挤压其它进程的可用内存）。
- 因此工程上做 **Pinned Pool**：初始化时一次性分配一大块 pinned 内存，运行时只管理 offset / Block ID（控制面与数据面分离）。截图里「本章沿用上一章初始化时一次性分配的 Pinned Pool，运行时只分配 Block ID」正是这个取舍。

## Pinned 一定比 Pageable 快吗？异步拷贝能「完全隐藏」传输吗？ #cuda #memory #dma #pinned-memory #performance #uva

> **速查**
> - **不一定，甚至可能更慢**：小传输时 pinned 的分配/管理开销可能超过重叠收益，pageable 的 staging 拷贝（CPU 侧内存到内存）反而更省事
> - 「能异步」≠「被隐藏」：kernel 短、或真依赖该数据时，stream 里仍是串行，异步提交无效
> - GPU 侧始终走同一条 PCIe —— pinned 省的是 CPU 侧路径，不减少传输量本身
> - pinned 页不可回收，过度使用挤压其它进程 → 拖慢整个系统
> - 第三条路：`cudaHostAllocMapped` + `cudaHostGetDevicePointer`（zero-copy / UVA），省显式拷贝，但每次访问走 PCIe、延迟高，仅适合只读一次且访问规律的数据

### 正文

**① 小传输：开销可能 > 收益**

pinned 的优势来自两点：DMA 能直接读，且能异步。但传输量很小时（几 KB）：

- 异步重叠省下的时间，小于 pinned 内存分配 / 管理的额外开销；
- GPU 侧还是得走同一条 PCIe，带宽没变；
- pageable 那次 staging buffer 拷贝是 CPU 侧的内存到内存拷贝，很快，可能比显式维护 pinned pool 更省事。

所以「小传输 + 一次性」场景，pinned 未必划算。

**② 「完全隐藏」是理想情况**

要隐藏传输，两个条件得同时成立：计算真的能和 DMA 并行，且计算时间长到盖住传输时间。

- kernel 很短 → 盖不住；
- kernel 依赖这块数据（真依赖）→ stream 里它必然排在拷贝之后，串行。

异步提交只是把传输排进 stream 队列，并不改变依赖关系。**能异步 ≠ 被隐藏。**

**③ 过度使用 pinned 伤整个系统**

pinned 页不可回收，分配过多会挤压其它进程的可用内存，系统整体变慢。这正是教程用 **Pinned Pool** 一次性分配、运行时只切 offset 的原因。

**④ 第三条路：zero-copy（UVA mapped）**

用 `cudaHostAlloc` 带 `cudaHostAllocMapped` 标志分配，再用 `cudaHostGetDevicePointer` 拿到设备侧指针，kernel 就能通过 UVA 直接访问主机内存 —— 省掉显式拷贝。

代价：每次访问都走 PCIe，延迟高。只在「数据只读一次、且访问模式规律」时划算。

## 为什么操作系统一定要分页？ #cuda #memory #dma #virtual-memory

> **速查**
> - 分页**不是为了 DMA 设计的**——它是为 CPU 分时系统设计的，DMA 是后来者，必须适应既成的规矩
> - 五个硬需求：① 物理内存超额订阅 ② **虚拟连续 ≠ 物理连续** ③ 进程隔离与保护 ④ 页面共享 ⑤ 换出
> - 最关键是 ②：把"虚拟连续"和"物理连续"解耦，否则物理内存碎片化会让大块连续分配永远失败
> - page 是虚拟内存做**所有事情**的最小粒度单位——换出、保护、共享、迁移、写时复制全挂在这个粒度上
> - 所以 pageable 是默认（服务 CPU，绝大多数情况），pinned 是例外（服务设备）

### 正文

**五个需求，逐条说**：

**① 物理内存超额订阅**
你开 20 个进程，每个 `malloc` 2 GB，物理内存只有 32 GB——这能跑，靠的就是"虚拟地址只是一张承诺，物理页按需给"。没有分页，`malloc` 必须立刻兑现物理内存，第一个进程就把内存吃光。

**② 虚拟连续 ≠ 物理连续**（最关键）
假设你要一块 1 GB **物理连续**内存。机器跑了三天，物理内存碎成上千块——哪怕空闲总量有 4 GB，也凑不出一块连续的 1 GB。**分页把"虚拟连续"和"物理连续"解耦**，于是"要一块连续的 1 GB"变成一件永远能办到的事。

**③ 进程隔离与保护**
每个进程一张页表，A 看不见 B 的物理页。权限位（R/W/X）挂在页表项上，由硬件强制执行。

**④ 页面共享**
同一份物理页可以映射进多个进程（共享库、`fork` 的 COW）。这是所有省内存技巧的地基。

**⑤ 换出**
冷页写进 swap 或直接丢弃（file-backed 页），热页留内存。这是"可用内存比物理内存大"的机制本身。

**这五条没有一条是为了 DMA。** 分页是 1960 年代为 CPU 分时系统设计的。DMA 是后来者，它必须适应一个已经存在的规矩，而不能反过来要求规矩为它改变。

结论：**pageable 是默认，因为它服务于 CPU——而 CPU 是绝大多数情况；pinned 是例外，因为它服务于设备——设备是少数，而且它对"稳定"的要求 CPU 从来没有过。**

## prefetch 能不能替代 pinned？ #cuda #memory #dma #pinned-memory

> **速查**
> - 不能。必须先把问题拆成**两个独立的问题**
> - **A｜页不在物理内存**（被换出了 / 从没碰过）→ prefetch **能**解决，挨个读一遍就全驻留
> - **B｜页在物理内存，但内核随时可以换出/迁移/回收** → prefetch **不能**解决
> - 关键认知：**"驻留"对 pageable 内存是尽力而为的状态，不是保证**
> - CPU 为什么无所谓——MMU 触发缺页异常，内核把页弄回来，**对 CPU 是正确性透明的**。而 **DMA 引擎不在这条路上**
> - 后果不是崩溃，是**静默数据损坏**——比崩溃可怕得多

### 正文

**问题 B 才是致命的那一半。** 你 `touch` 完所有页之后，内核在下一个毫秒仍然可以：

- **换出**——它判断这些页是冷的，或者系统内存压力上来了
- **迁移**——内存碎片整理（compaction）、NUMA balancing 会搬物理页
- **回收**——file-backed 页（比如 `mmap` 的文件）可以直接丢掉，反正能从磁盘重读

**CPU 为什么不受影响**：CPU 访问一个被挪走的页时，MMU 触发缺页异常，内核把它弄回来，CPU 完全无感。整个过程对 CPU 是正确性透明的。这是分页机制的核心设计。

**DMA 引擎为什么不行**：它拿到的是一串已经翻译好的物理地址，发出去读，然后收数据。中途页被换走了，它没有"缺页异常"这个概念，也没法暂停下来等内核。

**失败场景**：

```
prefetch 全部页  →  此刻确定驻留            ← 拿到的是一个"时刻快照"
        ↓
（内核在这之间可以自由换出/迁移/回收）
        ↓
提交 DMA  →  读到一半，第 700 个页被换走了
        ↓
无异常 · 无报错 · 数据是错的
```

**为什么不让 DMA 也走缺页那条路？** 历史上真有这条线：PCIe 的 **ATS**（Address Translation Services，让设备缓存地址翻译）和 **PRI**（Page Request Interface，让设备主动请求缺页），加上 IOMMU 支持，理论上设备可以像 CPU 一样按需缺页。但：

- 不是所有平台/设备都支持
- 一次缺页要走 PCIe 往返，**微秒级延迟**。对 CPU 是小事，对想把带宽跑满的 DMA 是灾难
- 高带宽场景根本不希望它在传输中途停下来

**结论**：prefetch 让你把"大概率驻留"变成"此刻确定驻留"，但 pin 给的是"传输全程持续驻留"。**前者是一个时刻的快照，后者是持续的保证。快照能被偷走，保证不能。**

## pin 是软件机制还是硬件机制？ #cuda #dma #pinned-memory

> **速查**
> - 机制本身是**纯软件**：内核加页引用计数、把页挂到 unevictable LRU 链表、迁移路径主动跳过
> - **硬件不感知"pinned"这个概念**——DMA 引擎只看到一串 IOVA，不知道背后是否被 pin
> - 没有任何硬件位强制"不许移动"——**是内核选择不移动它**。这是一个内核自愿遵守的约定
> - 证据：`RLIMIT_MEMLOCK` / cgroup 限额的存在，说明"能 pin 多少"是内核的策略决策，不是硬件约束
> - 硬件真正参与的是 **IOMMU 翻译**——pin 的效果通过"IOMMU 映射可以长期有效"体现出来

### 正文

**① 内核侧（软件）做四件事**：

- **加页引用计数**——页的 `_refcount` 不为零，回收器就不会碰它
- **把页挂到 unevictable LRU 链表**——一条专门存放"不可回收页"的链表，内存回收路径**根本不扫它**
- **迁移路径主动跳过**——内存整理和 NUMA balancing 搬页前会检查页有没有被 pin，被 pin 就绕开
- **记进 `mm->pinned_vm`**——受 `RLIMIT_MEMLOCK` / cgroup 限额约束。这就是 pinned 不能无限分配的原因

**② 硬件侧只看到"稳定的映射"这个结果**：

**DMA 引擎完全不感知"pinned"。** 它拿到的是一串 **IOVA**（I/O Virtual Address，设备侧使用的地址空间，由 IOMMU 翻译成物理地址），它只是发读写请求。

硬件真正参与的是 IOMMU：

```
CPU 侧：  用户态 VA  →  页表       →  PA
设备侧：  IOVA       →  IOMMU 页表  →  PA
```

驱动提交 DMA 前要把这块 buffer 的映射写进 IOMMU 页表。对 pageable 内存，这个映射**没法建**（物理页会变，建了也白建）——所以只能先 pin 再建映射，或者用 pin 住的 staging buffer 中转。

**③ 所以准确的回答是**：

> pin 是**内核自愿遵守的一个约定**；硬件（MMU / IOMMU / DMA 引擎）只是**受益于**"映射可以长期有效"这个结果。

**它不是硬件强制的。** 没有任何一根线、任何一个寄存器位阻止内核去移动一个 pinned 页——是内核*选择*不移动它。这是很重要的一点：pin 靠内核和驱动都守规矩。

**一个反直觉的推论**：pin 解决的是"**稳定性**"，不是"**连续性**"。很多人以为 pin 是为了拿到物理连续内存——不是。现代 DMA 引擎基本都支持 SGL（Scatter-Gather List），一次传输可以横跨许多不连续的物理页。**真正的约束只有一个：这些页在整个传输期间不许动。**
