# 熵编码

> 压缩算法系列 · **基础构件层**。熵编码器负责"按概率分配码字"，是压缩流水线的**最后一环**。
>
> **一句话纲要**：**建模（modeling）决定 H 有多小，编码器（coder）决定实际码长离 H 有多近。**
> 后面会看到——**压缩率的绝大部分收益来自建模，不来自换编码器**。
>
> **标注**：【软件】= 纯算法，跑在通用 CPU；【硬件】= 需要专门电路才划算；【软硬协同】= 软件定策略、硬件执行。

## Huffman 编码 #compression #entropy

> **速查**
> - **前缀码**：任何码字都不是另一个的前缀 → 不用分隔符就能唯一解码
> - **Kraft 不等式** `Σ2^(-lᵢ) ≤ 1` 是前缀码存在的**充要条件**（McMillan 定理把它推广到所有唯一可解码码）
> - **构造**：反复取出两个**最小概率**节点合并成新节点，放回堆 —— 贪心，`O(n log n)`
> - **最优性**来自"交换论证"：**两个最小概率符号可以设为最深层的兄弟**
> - ⚠️ **硬伤**：`H ≤ L_avg < H + 1` —— 那个 `+1` **是每符号的**（对比算术编码的"整条消息 ≤2 bit"）
> - **最大码长无上界保证** → 硬件/固件需要**长度受限 Huffman**（DEFLATE 限 15 bit，JPEG 限 16 bit）

### 正文

**前缀码的必要性**：码字之间无分隔符，从左往右读、一旦匹配到完整码字就是一个符号。

**Kraft 的必要性（直觉）**：把码字当二进制小数，长度 `l` 的码字占宽度 `2^(-l)` 的区间。前缀码保证任意两个码字的区间**互不相交**，全部落在 `[0,1)` 内 → 总宽度 ≤ 1。

**构造算法**：

```
把每个符号做成叶子节点，权值 = 其概率（或频次），放进最小堆
while 堆中节点数 > 1:
    a = 取出最小权值节点
    b = 取出次小权值节点
    建新内部节点 n，权值 = a.权值 + b.权值，左孩子 a、右孩子 b
    把 n 放回堆
剩下的唯一节点是根
从根到每个叶子的路径，向左记 0 / 向右记 1，即该符号码字
```

**最优性证明的两个要点**：

- **交换论证**：设最优树中概率最小的两个符号 x、y 不是最深层的兄弟。把最深层的两个叶子 a、b 与 x、y 对调。因为 x、y 概率最小，**不会增加**总代价 → 存在一棵同样最优、且"两个最小概率符号是最深层兄弟"的树。
- **最优子结构 + 归纳**：把这两个兄弟合并成一个概率为 `p_x + p_y` 的元符号，问题规模减 1。贪心每一步正好合并当前最小的两个，归纳可得全局最优。

**长度受限 Huffman**（硬件友好）：

- **问题**：Huffman 产生的最大码长无上界。对近似 Fibonacci 分布的频次，最大码长可以到 `n-1`。硬件/固件解码器希望有硬上界（比如 ≤15 bit），才能用固定大小的查找表。
- **典型上限**：DEFLATE **15 bit**；JPEG **16 bit**。
- **精确最优算法**：**package-merge**（Larmore–Hirschberg, 1990），`O(n·L)`。另有 Katajainen–Moffat–Turpin 的 `O(nL)` 方案。
- **启发式（zlib 走的路）**：先正常建 Huffman；若出现超长码字，就把频次做"削平"处理（降低大权值 / 抬高小权值），再重建，直到没有超长码字。**不保证最优**，但简单。
- **软硬协同点**：长度上界由**软件**设定（选 L、选算法），**硬件**解码表结构依赖这个上界来定尺寸。

## Canonical Huffman（规范 Huffman） #compression #entropy

> **速查**
> - **解决什么问题**：普通 Huffman 解码必须知道整棵树的形状，**传树代价不小**
> - **关键性质**：**只要传每个符号的码长，就能唯一确定所有码字** —— 不需要传树结构
> - **码长序列通常高度规律**，能用很便宜的游程编码压掉（DEFLATE / zstd 都这么做）
> - **分配规则**：① 长度短的码字数值小；② 同长度的按符号编号递增分配；③ 从 0 开始递增
> - **解码不用建树**：用 `first_code[len]` / `count[len]` / `first_sym[len]` 三个数组
> - **硬件友好**：小常数表 + 比较器阵列；也有"一次查 8/9 bit 得到符号+消耗比特数"的多比特查表变体

### 正文

**伪代码（zlib 风格）**：

```
count[len] += 1                     # 统计每种长度有多少个码字
next_code[len] 的递推：
    code = 0
    for len = 1 .. MAXLEN:
        code = (code + count[len-1]) << 1
        next_code[len] = code
# 给每个符号分配
for sym = 0 .. n-1:
    if L[sym] == 0: continue        # 该符号未使用
    code[sym] = next_code[ L[sym] ]++
```

**解码**：逐比特累积 `cur = (cur << 1) | next_bit`，长度 `len` 递增，当 `cur - first_code[len] < count[len]` 时命中，符号 = `first_sym[len] + (cur - first_code[len])`。

## 算术编码 / 区间编码 #compression #entropy

> **速查**
> - **思想**：把整条消息编码成 `[0,1)` 里的一个实数——每来一个符号，把当前区间按概率**切成子区间**，选中对应那个
> - **为什么能突破"每符号整数比特"**：码长是实数 `-log₂(p_消息)`，**整条消息总冗余 ≤ 2 bit，不随符号数增长** → 符号越多，每符号损失 → 0
> - **自适应**：不预传模型，编解码双方从相同初始模型出发、每处理一个符号后用同一规则更新 → 解码端无需额外传模型
> - ⚠️ **代价：严格串行** —— 符号概率依赖之前所有符号，无法先算好整段再并行
> - **进位问题的经典解法**：E1/E2（最高位相同就输出并左移）+ **E3（下溢）**——`low∈[0.25,0.5)` 且 `high∈[0.5,0.75)` 时用**待定计数（pending bits）**记下，稍后一次性补
> - **替代方案 carry-less range coder**（Subbotin）：字节为单位重归一化、限制区间宽度**避免进位**，损失极小的压缩率换实现简单和速度。**LZMA 用的就是这类**
> - **硬件实例**：JPEG 2000 的 **MQ coder**；H.264/HEVC/VVC 的 **CABAC**

### 正文

**区间细分示例**（二符号 0/1，`p₀=0.6, p₁=0.4`，消息 "10"）：

```
start [0,1)
符号 1：占 [0.6, 1.0)      → 当前 [0.6, 1.0)
符号 0：在 [0.6,1.0) 内再按 0.6/0.4 切
        [0.6, 0.6+0.4*0.6) = [0.6, 0.84)   → 当前 [0.6, 0.84)
```

区间宽度从 1 → 0.4 → 0.24，**宽度恰等于该消息的概率** `0.4·0.6 = 0.24`。

**E3（下溢）**：当 `low ∈ [0.25,0.5)` 且 `high ∈ [0.5,0.75)`，二进制前缀是 `01...` 和 `10...`，高位不同但第二位固定为 0 和 1。此时无法直接输出，把这段"未定"的位记一个**待定计数**，缩小并左移，等后面再一次性补上正/反位。

**算术编码 vs range coder**：算术编码的位精确定义清晰但进位麻烦；range coder 用**字节重归一化**换取实现简单和速度，压缩率损失极小。

## ANS（非对称数系编码） #compression #entropy

> **速查**
> - **目标很明确**：**拿到算术编码的压缩率，同时拿到 Huffman 的表驱动速度**
> - **核心思想**：用**单个整数状态 x** 表示整个编码进度，而不是 `low/high` 一对
> - **编码**：`x = (x // f_s) * M + (x % f_s) + c_s`；位宽不够时把低位吐到码流（重归一化）
> - **解码**：`slot = x & (M-1)` 查表得符号，再逆向还原
> - ⚠️ **ANS 的状态演进是"后进先出（栈式）"** —— 解码出符号的顺序是编码顺序的**逆序**。实际使用要么倒序编码、要么倒序解码
> - **M 取 2 的幂**时，除法和取模**都消失**，只剩一次乘法；**tANS 连乘法都去掉**，退化为纯查表 + 移位
> - **为什么适合硬件**：单整数状态 + 纯算术（乘/移位/查表）+ **无进位传播** + **可交织成 N 条独立流并行**
> - **推广关系**：频率取 2 的幂 → 退化成 Huffman；量化精度做大 → 逼近算术编码。**ANS 是把两者统一在一个框架里**

### 正文

**记号**：符号 s 的频率 `f_s`，累计起点 `c_s = Σ_{t<s} f_t`，总数 `M = 2^scale_bits`。状态下界 `RANS_L`，重归一化基数取 2^8（字节）时不变式是 `x ∈ [RANS_L, RANS_L·256)`。

**rANS 编码**：

```
x_max = ((RANS_L >> scale_bits) << 8) * f_s
while x >= x_max:                 # 一般最多一次
    output_byte(x & 0xFF)
    x >>= 8
x = (x // f_s) * M + (x % f_s) + c_s
```

无除法版本：预计算 `(1<<k)/f_s` 用乘法近似（别名法 alias method 可做到 O(1) 查表）。

**rANS 解码**：

```
slot = x & (M - 1)
(sym, f_s, c_s) = table[slot]
x = f_s * (x >> scale_bits) + slot - c_s
while x < RANS_L:
    x = (x << 8) | read_byte()
```

**tANS（表驱动 ANS）**：把"符号 + 状态"的转移全部**预计算成表**。Yann Collet 的 **FSE** 就是 tANS，用在 zstandard、LZFSE 里。

```
entry = DT[x]                 # x ∈ [0, L)
emit entry.symbol
x = entry.baseline + read_bits(entry.k)
```

表由**软件离线构建**（依赖分布），运行时是纯 LUT + 移位 + 读位流。

**与算术编码的本质区别**：

1. 状态是**单个整数**，没有 low/high 的进位传播 → **无 E3 下溢问题**，硬件简单
2. 天然支持"用表换速度"（tANS）或"用精确频率换压缩率"（rANS）
3. **自适应更难**：由于编解码方向相反（栈式），自适应要跑两遍模型（正序统计一次、逆序编码一次）。**ANS 对静态分布最合适**

**并行靠交织**：ANS 单流本身串行，但可以把数据切成 N 条独立子流、每条一个状态、N 路并行编解码。这是 SIMD 和硬件多通道的标准做法。

## 上下文建模：PPM 与 CM #compression #entropy

> **速查**
> - **核心事实**：**压缩率的上限由模型给出的概率决定**。同一符号，模型估计的 `p_s` 越准，`-log₂(p_s)` 越小
> - **Huffman 还是 ANS 只决定你离这个下界有多近**
> - **所以"建模通常比编码器更决定最终压缩率"**
> - **PPM**（Prediction by Partial Matching）：同时维护多个阶（0~5 阶）的统计，高阶没命中就发**逃逸符号**、退到低阶
> - **CM**（Context Mixing）：维护**大量**模型，用**混合器**加权合并，权重通过类似在线梯度下降自适应（**PAQ / lpx / CMIX**）
> - **收益对比的硬道理**：编码器差距有**硬上界**（最优前缀码 `< H+1`；算术编码总冗余 `≤2 bit`）；**模型给出的 H 本身没有小上界**——收益空间是开放的
> - 现代压缩器都在两边同时下功夫：LZMA = LZ77 + **上下文相关的字面量建模** + range coder

### 正文

**为什么建模更决定压缩率**：同一个文件，换编码器（Huffman→ANS）通常只能省几个百分点；换模型（加高阶上下文、混合更多预测）**可以省 20%~50%**。

- 编码器的理论性能差是**有界的**：最优前缀码 `L < H+1`；算术编码总冗余 ≤ 2 bit
- 模型给出的 H 本身**没有小上界**——模型越强，H 越小

> **"编码器是常数因子，模型是指数级变量"** 是理解这一族的纲要。

## 各方法代价对比 #compression #entropy

> **速查**
> - **压缩率排序**：CM > PPM > rANS/tANS > 算术 > Huffman（**越前越慢越耗内存**）
> - **速度排序**：大致反过来
> - ⚠️ **"并行性"指同一条码流内**。ANS/Huffman 真正的高速并行都靠**多流交织**，不是把单流拆开
> - ⚠️ **ANS 因栈式方向，自适应要额外跑一遍模型** —— 对静态分布最合适

### 正文

| 方法 | 压缩率 | 编码速度 | 解码速度 | 内存 | 并行性 | 流式/自适应 |
|---|---|---|---|---|---|---|
| Huffman | 差（`H`~`H+1` 比特/符号） | 快 | 快 | 低 | 较易 | 流式可；静态模型 |
| Canonical Huffman | 同 Huffman | 快 | **更快**（表驱动，无建树） | 低 | 较易 | 流式可；只传码长表 |
| 算术 / range coding | **最好**（≈H，总冗余≤2 bit） | 慢 | 慢 | 低-中 | **难（严格串行）** | **自适应最好** |
| rANS | ≈算术编码 | 快 | 快 | 低 | 交织并行 | 需先验分布 |
| tANS / FSE | 优于 Huffman，略逊 rANS | 很快 | 很快 | 低（固定 2^R 表） | 交织并行 | 需先验/同步分布 |
| PPM | 很高 | 慢 | 慢 | 高 | 有限 | 流式可；自适应 |
| CM（PAQ 类） | **最高** | 很慢 | 很慢 | 很高 | 有限 | 流式可；自适应 |

**归属总表**：

| 环节 | 归属 | 说明 |
|---|---|---|
| Huffman 树构造、package-merge | 【软件】 | 离线算法 |
| Canonical Huffman 码长表生成 | 【软件】 | 传码长即可 |
| Canonical Huffman 解码 | 【硬件】/【软硬协同】 | 小常数表 + 比较器阵列 |
| 算术编码区间运算、E1/E2/E3 | 【软件】 | 进位处理是软件实现难点 |
| MQ coder / CABAC | 【硬件】 | 专用二进制算术编码通路 |
| rANS 编解码 | 【软硬协同】 | 算法软件定，运行是乘/移位/LUT |
| tANS / FSE | 【软硬协同】 | 表软件构建，运行是纯 LUT + 读位 |
| 多流交织并行 | 【软硬协同】 | 软件切流，硬件/SIMD 并行通道 |
| PPM / CM 建模与混合 | 【软件】 | 模型策略与统计表 |
| 上下文固定表（CABAC contexts） | 【硬件】 | 上下文表落进硬件 |

## 一页速记

- 前缀码 ⟺ 区间不重叠 ⟹ Kraft `Σ2^(-l)≤1`；它刻画了所有唯一可解码码的可达域
- **Huffman** = 反复合并两个最小概率节点；最优性来自交换论证
- Huffman 每符号最多损失 <1 bit；**算术编码把损失压到整条消息 ≤2 bit**
- **Canonical Huffman**：只传码长表，码字由"同长内按符号序、短码小、从 0 递增"唯一确定
- **ANS** = 单整数状态 + 数论变换；`x'=(x/f)·M+(x mod f)+c` 编码，`x=f·(x>>n)+(slot-c)` 解码
- ANS 栈式（编解码方向相反）；tANS 做成纯 LUT，rANS 保留精确频率；**两者靠多流交织并行**
- **压缩率主要由模型决定**，编码器只决定"离模型熵有多近"

## 不确定项

- 长度受限 Huffman 各精确算法的常数与细节、"哪种实现用哪个变体"，随代码库不同，未逐一核对
- 自适应 ANS 的工程细节与相对算术编码的实际收益，需按场景实测，**无具体 benchmark 数据**
- rANS/tANS 具体吞吐数值强依赖 CPU/表大小/交织路数，**不应作为绝对值引用**
- AV1 的熵编码器（多符号自适应区间编码，带 CDF 更新）与经典算术编码同族，但不同文献叫法不一
- tANS 扩散函数的精确形式：FSE 用基于步长的确定性扩散，具体常数未逐行核对源码
