# 现代通用压缩格式与工程取舍

> 压缩算法系列 · **格式层**：把 LZ77、熵编码等基础构件组装成实际可用的**格式**。
>
> ⚠️ **一个前提**：压缩**格式**本身永远是【软件】——它是一份字节布局规范。硬件只在加速某个子步骤时介入，属于**实现层**，不是格式定义的一部分。
>
> ⚠️ **数字纪律**：第 6 节所有绝对值**不要跨表复述**——原始来源的硬件/版本/语料不同，只有**同表内**和**量级**可信。

## DEFLATE / zlib / gzip / zip #compression #format

> **速查**
> - DEFLATE（RFC 1951）只用了**两个**构件：**LZ77 + Huffman**
> - LZ77 部分：窗口**固定 32 KiB**（回指距离上限 32768）；匹配长度 **3–258**；**相隔超过 32 KiB 的重复串无法被引用**
> - Huffman 部分：每个块用**两棵**独立的树——一棵管 literal + 长度，一棵管距离
> - 块类型三种：**stored**（不压缩）/ **fixed Huffman**（预定义码表）/ **dynamic Huffman**（块头传自定义码表，最常用）
> - zlib 对外是级别 **0–9，默认 6**，内部其实是**两条代码路径**：`deflate_fast`（1–3，不做 lazy matching）vs `deflate_slow`（4–9，做 lazy matching）
> - ⚠️ **级别越高越慢、输出越短，但解压速度基本不变**（解压复杂度只取决于数据本身）——这是 LZ 系算法的共同性质
> - **为什么成了事实标准**：RFC 1951 **无专利**（IBM 早年关键 LZ 专利 1990s 到期是前提），加上 gzip + zlib 广泛嵌入操作系统、语言标准库、HTTP、PNG、ZIP——**兼容性而非压缩率**

### 正文

**四个容易混的层次**：

| 层 | 是什么 | 有什么 |
|---|---|---|
| **DEFLATE** | 纯**压缩数据流**规范（RFC 1951） | 无文件头、无文件名、无校验和 |
| **zlib 格式** | DEFLATE + 2 字节头 + 4 字节 **Adler-32** 校验（RFC 1950） | |
| **gzip** | 更大的头 + 尾（RFC 1952） | magic `1F 8B`、CM=8、MTIME、XFL、OS；**尾部是 CRC-32 + ISIZE** |
| **zip** | 更上层的**归档容器**（PKWARE APPNOTE） | 一个 zip 里多个文件 + 目录结构 + per-file 头，每个条目**可选**用 deflate |

> ⚠️ **zip 不是"一种压缩算法"**，是"带目录 + 可选 deflate"的归档格式。

**【硬件】** gzip 的 **CRC-32 校验**可以走 CPU 指令加速（x86 的 `crc32` 属 SSE4.2；ARMv8 有 CRC 扩展）。⚠️ **注意 gzip 用的是 CRC-32 而非 CRC-32C，二者多项式不同，指令通常算的是 CRC-32C，需要软件换算。** 这是**校验和**被硬件加速，不是压缩本身。

## LZMA / LZMA2 / xz #compression #format

> **速查**
> - 与 DEFLATE 的三处关键差异，**都指向"压缩率换时间"**
> - **① 熵编码器换成 range coder + 自适应二进制模型**（每个 bit 有自己的概率估计，且**随解码在线更新**）
>   - 为什么这是主因：Huffman 只能整数 bit。**符号概率 0.9 时理论下限约 0.15 bit，Huffman 最少也得给 1 bit**
> - **② 字典大 = 窗口大**：从 4 KiB 到 **4096 MiB − 1 字节**（对比 DEFLATE 的 32 KiB）
> - **③ 匹配器更贵**：hash chain / binary tree（`bt4`、`hc4`）+ **近似最优解析**
> - **LZMA1 vs LZMA2**：LZMA2 把数据切块、每块可重置字典/换参数、支持未压缩块；**解码原始 LZMA2 流只需知道字典大小**（LZMA1 还要 `lc`/`lp`/`pb`）
> - **xz 是容器不是算法**：Stream Header → 若干 Block → Index → Footer；支持多线程分块并行

### 正文

**为什么"压缩率好但慢"**：三件事叠加——更大的字典（搜索代价高）+ 更贵的匹配搜索 + 更精细但更慢的自适应 range coding。**解码侧同样慢于 zstd/deflate**，因为 range coder 是逐 bit 状态机，无法像 Huffman 那样纯查表高速展开。

## zstd（Zstandard） #compression #format

> **速查**
> - **三阶段流水线**：LZ77 匹配 → 熵编码 → 帧/块结构
> - 熵编码分工：**literal 用 Huffman**（最大码长 11 bit）；**序列三元组 `(litLen, matchLen, offset)` 用 FSE（tANS）**
> - **FSE 是 zstd 相对 DEFLATE 的压缩率来源** —— 查表式算术编码，比 Huffman 更接近熵下限、又比传统算术编码快得多
> - 块最大 **128 KiB**（解压后）；块类型 raw / RLE / compressed
> - 级别 **1–22**（20–22 为 `--ultra`）。低级别近似 LZ4 速度 / deflate 压缩率；高级别逼近 xz 压缩率但快得多
> - ⚠️ **解压速度与压缩级别基本无关** —— 适合"压缩一次、解压多次"的存储/传输场景
> - **字典训练**（`zstd --train`）：给小文件一段"预置历史"，解决"小文件开头没有历史、压缩率差"的问题

### 正文

**字典训练的官方经验值**：

- CLI：`zstd --train <样本集>`；底层 API `ZDICT_trainFromBuffer()`，默认走 **fastCover** 算法
- 字典大小 **~100 KB** 量级；样本**数千个**；**样本总大小 ≈ 目标字典大小的 100 倍**
- **收益最大**的场景：**每个文件 < 128 KB** 且**结构相似**
- 字典本身也是合法 zstd 数据，能跨库/跨语言复用

**注意**：字典训练是**软件**预处理步骤，训练成本一次性，收益在大量小对象上摊薄。

## brotli #compression #format

> **速查**
> - 仍是 **LZ77 + Huffman**，但加了两样 DEFLATE 没有的
> - **① 二阶上下文建模**：literal 的 Huffman 编码**不按全局统计**，而是按"**前两个已解码字节**"选上下文；距离的上下文取决于**当前拷贝长度**
> - **② 内置静态字典**：**122784 字节（≈120 KiB）**，约 **13504 个词/音节**，覆盖英/西/中/印地/俄/阿拉伯语 + HTML 标签 + CSS/JS 记号；每个词还能经过 **121 种变换**
> - 窗口 `lgwin` 范围 10–24，**默认 22（= 4 MiB）**；质量档 0–11，**默认 11**
> - **为什么 Web 场景常用**：内置字典对**短文本**天然占优（Web 响应常常很短）+ 上下文建模对标记语言高效 + **只压缩一次、分发无数次**（CDN 预压缩，压缩慢无所谓）
> - HTTP `Content-Encoding: br`、**WOFF2 字体**都基于 brotli

### 正文

> ⚠️ 官方口径宣称替换 gzip 后文本压缩密度约提升 **20%** —— **这是官方/百科口径，非独立复测**。

## LZ4 / Snappy / LZO：极速档 #compression #format

> **速查**
> - 共同哲学：**几乎放弃压缩率，换取极高吞吐**
> - ⚠️ **三者只做 LZ77，不做熵编码** —— 没有 Huffman、没有算术编码，**因为熵编解码正是最耗时的部分**
> - **LZ4**：块格式，解码器极简，解压接近内存带宽。有 **acceleration** 参数；另有 **LZ4_HC**（高质量模式，压缩很慢，**但输出仍能被标准 LZ4 解码器解**，解压速度不变）
> - **Snappy**：Google 出品，避开熵编码、跳过多步最优解析、对 64-bit x86 与未对齐读取优化，**无汇编**
> - **LZO**：三者里解压**最慢**
> - ⚠️ **三者的压缩率挤在 ~2.0–2.1 这个窄区间** —— **压缩率几乎是平局，差异全在速度**
> - **为什么压缩率会平局**：都用近似的最小匹配策略，主要差异在实现工程与解码器复杂度，**不是算法上限**。要拉开差距必须加熵编码或最优解析（那就是 zstd/xz 的地盘）

### 正文

| | LZ4 | Snappy | LZO |
|---|---|---|---|
| 熵编码 | 无 | 无 | 无 |
| 窗口 | 默认 ~64 KB（可更大） | ~64 KB | 与 LZ4 同量级 |
| 官方速度口径 | 压缩数百 MB/s、解压数 GB/s | 压缩 **≥250 MB/s**、解压 **≥500 MB/s** | 压缩 ~650 MB/s、解压 ~800 MB/s 量级 |

内存：LZ4 压缩约需 32 KB，**解压不需要额外内存**。

## 格式设计里的通用取舍 #compression #format

> **速查**
> - **窗口/字典大小**：越大 → 压缩率越高；代价是**编解码内存**都增长、编码搜索更慢。"**字典 ≈ 窗口，只是'预置且双方约定'的窗口**"
> - **熵编码器**：Huffman（快，但每符号≥1 bit）< FSE/tANS（**介于两者：接近算术编码压缩率、接近 Huffman 速度**——zstd 的核心卖点）< 算术/range coding（压缩率最高，但慢）
> - **块大小**：**大块** → 熵统计更准、表头占比低 → 压缩率好；但**随机访问粒度粗、内存峰值高**。**小块** → 易并行、易随机访问；但每块重建熵表、**块间无法互相引用**
> - **并行化能力**：取决于格式是否允许"**块独立**"。跨块引用会**破坏并行性**
> - **匹配搜索策略**：贪心/惰性（快）vs 最优解析/代价优化（慢）

## 流式与随机访问 #compression #format

> **速查**
> - ⚠️ **根本张力**：**压缩率来自"跨距离复用历史"，随机访问要求"把历史切断"**
> - LZ 压缩是**有状态**的：解码位置 i 的内容可能引用位置 i−k 的字节 → **压缩流天然是"从头顺序解"**
> - **跨块引用**：块 N 可引用块 N−1 的历史 → 压缩率高，但**必须顺序解码**
> - **块独立**：每块自成一解压单元 → 可**任意跳块、可并行**，代价是压缩率下降
> - **zstd 的 seekable 变体**：把数据切成多段、每段一个独立 frame；在**末尾**追加一个 **skippable frame**（规范要求所有解码器**跳过**的帧类型）装 seek table → **标准 zstd 解码器完全不感知 seek 表也能正常解压全文件**（向后兼容）
> - ⚠️ **代价（第三方实测）**：Go 源码上 **1 MiB frame 损失约 2.5%**，**64 KiB frame 损失约 17%**
> - **对比**：gzip/zlib 是纯线性流，**没有**标准随机访问机制；zip 的 per-entry 随机访问是**归档层**把每个文件独立存的功劳，**不是单个压缩流内部**的随机访问

### 正文

**zstd seekable 的机制**：

1. 把数据切成多段，每段压成一个**独立 frame**（每段一个入口点）
2. 末尾追加 **skippable frame**（magic `0x184D2A5E`），里面是 **seek table**（每段的压缩大小、解压大小，可选校验和）
3. 取子区间时：读文件末尾的 **9 字节 footer**（`Seekable_Magic_Number = 0x8F92EAB1`），定位 seek 表，再用累计偏移 seek 到目标 frame

**seek table footer** = `Number_Of_Frames`(4B) + `Seek_Table_Descriptor`(1B) + magic(4B)。官方建议 frame 别小于几 KiB。

## 硬件层面的现实：格式本身是软件，加速靠外挂 #compression #format #hardware

> **速查**
> - **格式 = 软件**：DEFLATE、LZMA2、zstd、brotli、LZ4 都是**字节布局规范**。**没有哪个通用格式在规范里规定"必须有硬件"**
> - **可被硬件加速的子步骤**：校验和（CRC/Adler，CPU 指令或专用单元）· 整体编解码引擎（Intel QAT、FPGA、SoC 压缩引擎）· Huffman/FSE 查表（SIMD/专用流水线）
> - ⚠️ **这类加速不改变格式**，只是"同一个格式换一种执行载体"
> - ⚠️ **判断某产品是否用硬件加速，要看它的实现声明，不能从"用了 zstd"推断**
