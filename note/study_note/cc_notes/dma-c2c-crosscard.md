# 片内 C2C/D2D 与跨卡 DMA

## 片内 C2C/D2D 与跨卡 DMA 的设计轴 #dma #noc #arch

> **速查**
> - 难点不是"做一个 copy 引擎"，而是**一个引擎横跨两个传输域**：片内 D2D 和跨卡
> - 两个域延迟差两个数量级（片内 ~100 ns vs 跨卡 ~1 µs+），一致性模型和错误语义都完全不同
> - RDMA 那套三件套在片内会退化：**不需要内存注册**（无 OS 换页）、**描述符环可能太重**（延迟占比过高）、**完成通知用 mbarrier 而非中断**
> - 六个设计决策：地址模型 / 前端统一还是分离 / 延迟差异不能外溢 / 跨卡写何时对本地 SM 可见 / 仲裁与 QoS / 错误重试不进片内路径
> - 最容易做错、症状最难查的一条：**跨卡写的一致性**——做错会间歇性读到旧数据

### 正文

**两个传输域的差异**：

| | **片内 D2D**（die ↔ die） | **跨卡**（GPU ↔ GPU） |
|---|---|---|
| 典型延迟 | ~100 ns 量级 | NVLink ~1 µs；走 PCIe ~2 µs 以上 |
| 带宽量级 | TB/s（如 Blackwell 双 die 间约 10 TB/s） | NVLink 4 约 900 GB/s/卡；PCIe 5 x16 约 64 GB/s |
| **寻址** | 本地物理地址通常够用 | **必须显式表达"远端"** |
| **一致性** | 硬件协议保证，或 NC-NUMA 下需显式处理 | 弱得多，通常只保证点到点有序 |
| 完成通知 | 片上信号 / mbarrier，ns 级 | 过链路往返，µs 级 |
| 错误 | 基本不会失败（失败=硬件 bug） | 链路可能降速或断，需要重传 |
| 流控 | 片上信用流控 | 独立链路层协议，另一套信用/重传机制 |

（数字为量级，按具体型号手册核。）

**注意最刺眼的两行：寻址和一致性。** 片内这两件事几乎不存在，跨卡这两件事是整个设计的核心。

**六个设计决策**：

1. **地址模型**——软件怎么表达"我要写到另一张卡"？
   - A：全局地址空间（各卡显存映射到同一地址空间不同段），描述符只给地址，需要一次译码 `地址 → 哪个卡 + 卡内偏移`
   - B：描述符带 `device_id`，实现简单但软件要显式区分本地/远端
   - C：两者都有，本地走快路径
   - 归属：【硬】地址译码 + 路由判定；【软】描述符构造

2. **前端统一还是分离**——前端必然要判断"目标是本地还是远端"再选路径。
   - 一个前端 + 两条后端：软件接口统一，但前端延迟被慢的那条拖累
   - 两个前端：各自最优，但软件要选，且两条路径语义要对齐
   - **代价提醒**：片内 100 ns 的传输若强制走异步 + 完整描述符流程，开销可能比传输本身还大

3. **延迟差异不能外溢**——片内传输软件可以同步等，跨卡 2 µs 必须异步。若共用一套完成机制，跨卡的延迟会污染片内路径。常见做法是分级完成通知：片内用硬件屏障，跨卡用带序号的完成事件。

4. **跨卡写的一致性**——要具体回答"对端 SM 什么时候能安全读到我写过去的数据"。
   - 不经过对端一致性域 → 需要显式 fence/信号通知对端"数据到了"
   - 走一致性路径 → 硬件保证，但每次写都要参与一致性协议
   - **做错症状：间歇性读到旧数据**

5. **仲裁与 QoS**——跨卡链路窄、延迟大、容易积压。若与片内关键路径共用仲裁器，跨卡排队延迟会传导到片内。需要明确优先级或带宽配额。

6. **错误重试不能进片内路径**——跨卡需要重传状态机。若与片内路径共用，会给片内路径引入不必要的面积和延迟。

**研究空白**：公开文献里，片内搬运（TMA、C2C）和跨卡搬运（NVLink 传输引擎）基本是两套独立设计，**同时管两个域的公开设计很少**——"统一 vs 分离"这个取舍本身可能是一个贡献点。

## 跨卡搬运的延迟是怎么被吸收的？ #dma #noc

> **速查**
> - 一条不能违反的等式：**在飞的字节数 = 带宽 × 往返延迟**（Little's Law 在链路设计里的形式）
> - 代入 NVLink 4：450 GB/s（单向）× ~1 µs ≈ **450 KB** 必须在飞
> - **关键：这不是"引擎里放一个 450 KB 缓冲"，而是一次传输被切成很多小包，每个包占一个独立追踪表项，全部并发在飞**
> - 四个吸收结构：**outstanding 事务表 / replay buffer（重传缓冲）/ 信用计数器 / 响应追踪表**——都在**链路控制器**里，不在 DMA 引擎里
> - DMA 引擎看到的只有"还能不能继续发"（信用）这一个信号；延迟的会计、重传、排序全在链路控制器
> - **读和写不对称**：写是 posted，发出去就不管（只需链路层 ACK）；读必须为每个未完成请求保留状态直到数据回来——这是高延迟场景偏好"写"的原因

### 正文

**吸收延迟靠的是"大量并发事务"，不是"一个大缓冲区"。**

一次 1 MB 传输，若包大小 256 字节，就是 4096 个包。它们各自独立在飞，不需要排队等待。所以链路必须能容纳这么多**同时未完成的事务**。

**四个结构各管什么**：

| 结构 | 作用 | 大小由谁定 |
|---|---|---|
| Outstanding 事务表 | 记录每个已发出未完成的事务 | **带宽 × 延迟 ÷ 包大小** |
| Replay buffer | 保存未被确认的包副本，出错时重传 | 链路层重传窗口 |
| 信用计数器 | 对端通告"还有多少接收缓冲"，发送方据此决定还能发多少 | 对端缓冲深度 |
| 响应追踪表 | 匹配读响应属于哪个请求 | outstanding 的读请求数 |

**都是 SRAM/寄存器阵列，在链路控制器里。**

**写与读的不对称**：

| | 写 | 读 |
|---|---|---|
| 语义 | Posted——发出去就不管，只需链路层 ACK | 必须等响应数据回来 |
| 需要追踪什么 | 只需重传窗口 | **为每个未完成的读保留状态，直到数据回来** |
| 高延迟下的表现 | 天然流水化 | 每个读占用一个表项一整个往返周期 |

**这就是高延迟场景偏好"写"的原因**——写不需要在源端保留状态。

## 为什么链路控制器独立于 DMA 引擎？ #dma #noc #arch

> **速查**
> - 判断某个结构该放哪的判据：**它是"线路"的属性，还是"传输"的属性？**
> - **信用计数器**和 **replay buffer** 记的是线路的账——**必须**在链路层，放在别处会算错账
> - **Outstanding 表**记的是传输的账——**可以**在客户端，但放在链路层有三种顺手的好处
> - 信用是**共享资源**（一条链路服务 SM 访存 / 原子操作 / 一致性消息 / DMA），多个客户端各记各的账必然对不上
> - 两条物理约束：**时钟域不同**（flit 周期亚纳秒 vs 软件时间尺度）+ **位置不同**（SerDes 必须在芯片边缘）
> - **分开的代价**：多一层握手延迟 + **信息在接口上被压平**（引擎知道"这批要优先"，链路只看到"一个写请求"）

### 正文

**三类结构的归属理由不同**：

| 结构 | 是什么的属性 | 必须放哪 |
|---|---|---|
| 信用计数器 | **线路**——对端接收缓冲还能装多少 flit | **必须**在链路层 |
| Replay buffer | **线路**——已发出但未被确认的包 | **必须**在链路层 |
| Outstanding 事务表 | **传输**——"我发出去了哪些请求" | 可以在客户端，通常仍在链路层 |

**信用为什么必须是链路级**：一条 NVLink 上跑的不只是 DMA 拷贝，还有 SM 直接访存、跨卡原子操作、一致性协议的探测/失效消息。**它们共用同一条物理链路，也就共用同一份信用池。** 对端只有一个接收缓冲，多个客户端各记各的账必然对不上——所以信用必须有一个**唯一记账点**。

**重传为什么必须是链路级**：重传的粒度是**链路包**。一次 1 MB 传输切成上千个包，可能第 700 个 CRC 错要重传。**重传窗口的大小由链路往返时间决定，和 DMA 传输的大小毫无关系。**

**outstanding 表放在链路层的三个理由**：① 读响应第一个到达链路控制器，匹配事务最省事；② 超时重发走链路，统一处理更简单；③ 排序保证需要看到全局顺序。

**两条物理约束**：

- **时钟域**：SerDes 速率到 25–50 Gbps 时 flit 周期是亚纳秒级，DMA 引擎在 µs–ms 尺度。在亚纳秒时钟域里塞描述符解析器既浪费面积又拖垮时序收敛。
- **位置**：NVLink 是 SerDes 必须出封装、必须在芯片边缘；Copy Engine 在芯片内部。flit 处理的时序约束要求它和 SerDes 在一起。

**分开的代价**：

| | 分开 | 合并 |
|---|---|---|
| 复用 | 一条链路服务多种流量 | 每个使用者重新实现 |
| 时钟收敛 | 两域隔离，干净 | 引擎时序被 SerDes 拖累 |
| **额外延迟** | **多一层握手 + 背压路径变长** | 少几拍 |
| **信息损失** | **引擎知道"要优先"，链路只看到"一个写请求"** | 优先级信息不丢 |

**推论**：outstanding 表的大小由**链路**决定，不由**引擎位置**决定。把引擎从芯片内部挪到链路边缘，消掉的只是片上穿越那几十纳秒（占往返 ~1 µs 的百分之几），**链路往返不动，账本就不动**。

**片内为什么没有这一层**：片上互联假设"送达是保证的"，没有 CRC、没有重传、没有信用流控。**这一整层不存在**——这才是片内和跨卡的本质差别，比"延迟高低"更根本。

**对统一引擎的含义**：能统一的只有**事务级**那部分（地址、长度、完成标识）；**链路级那部分统一不了**——它本来就不在你的引擎里。

## 跨卡 DMA 放在哪里？三条路径 #dma #noc

> **速查**
> - NVIDIA 的 GPU 里**没有"一个跨卡 DMA 引擎"**——跨卡搬运走**三条不同的路径**
> - **路径一**：`cudaMemcpyPeer` → 走 **Copy Engine（CE）**，独立的 DMA 引擎，每卡多个，对 SM 透明
> - **路径二**：SM 直接 `ld/st` 对端显存（靠 **UVA** 统一虚拟寻址）→ **根本不经过 DMA 引擎**
> - **路径三**：NIC ↔ GPU（**GPUDirect RDMA**）→ 网卡直接 DMA 进显存
> - 位置规律：**NVLink 控制器在芯片边缘**（SerDes 必须出封装）；**吸收延迟的四个结构都在它里面**
> - 多 die 的 GPU 里 die 之间**不走 NVLink**，走 **NV-HBI**（封装内，延迟低一个数量级）

### 正文

**三条路径各自谁在参与**：

```
路径一（显式拷贝，如 cudaMemcpyPeer）：
SM（不参与）→ Copy Engine → 内部互连 → NVLink 控制器 → 对端

路径二（SM 直接访问对端显存）：
SM → L2 → 内部互连 → NVLink 控制器 → 对端
（没有 DMA 引擎参与；靠 UVA 让所有卡的显存映射到同一虚拟地址空间）

路径三（NIC ↔ GPU）：
网卡 → PCIe/NVLink → GPU 显存
```

**路径二为什么不需要 DMA 引擎**：SM 发的是一条普通的 `ld/st` 指令，硬件根据地址段判断目标是本地还是远端，自动路由。对 SM 来说，访问远端显存和访问本地显存是**同一条指令**，只是延迟和带宽不同。

**Copy Engine 的位置**：不在 SM 里，是芯片上与 SM 平级的一个独立单元，一张 GPU 上有多个，可以并行跑多路拷贝。

**一个设计选择**：跨卡流量**通常绕过本地 cache**（L1/L2）。远端延迟太高，缓存它性价比低，而且会引入跨卡一致性维护成本。所以跨卡读一般是"穿透读"。

**多 die 的情况完全不同**：Blackwell 那样一个封装里两颗 die，die 之间走 **NV-HBI**，带宽量级比 NVLink 高一个数量级，延迟低得多——因为距离就是封装内几毫米。**这意味着"统一引擎"面对的是两个不同性质的链路控制器。**
