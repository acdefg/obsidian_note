# 地址空间与翻译

## MMU 和 IOMMU 有什么区别？ #dma #iommu #arch

> **速查**
> - 两者都做地址翻译，区别在**谁在用**：MMU 服务 CPU 核，IOMMU 服务外设的 DMA 引擎
> - MMU 翻译进程虚拟地址 VA → 物理地址 PA；IOMMU 翻译设备侧地址 **IOVA**（I/O Virtual Address，设备发出的地址，不是物理地址）→ PA
> - 页表归谁管：MMU 每个进程一套，根指针在 CPU 寄存器（x86 是 CR3）；IOMMU 每个设备（准确说是每个 IOMMU 域）一套，由**驱动**在提交 DMA 前建立
> - IOMMU 最初的主要动机是**安全**，不是方便——没有它，有 bug 或恶意的设备可以 DMA 到任意物理页
> - 别名：x86 上 Intel 的实现叫 **VT-d**，AMD 的叫 **AMD-Vi**；ARM 上叫 **SMMU**（System MMU）

### 正文

| | **MMU** | **IOMMU** |
|---|---|---|
| 位置 | 在 CPU 核心里，每核一个 | 在设备到内存的路径上，通常集成在 SoC 互连或内存控制器旁 |
| 谁在用 | CPU 核 | 外设的 DMA 引擎（GPU、NVMe、网卡……） |
| 翻译什么 | VA → PA | IOVA → PA |
| 页表归属 | 每进程一套 | 每设备/域一套，驱动建立 |
| 缺页怎么办 | CPU 触发缺页异常，陷入内核处理 | 设备通过 PCIe 的 **PRI**（Page Request Interface）请求缺页，需硬件支持，实践中很少用于高带宽路径 |
| 主要目的 | 进程隔离、按需换页、内存共享 | DMA 隔离、地址翻译、虚拟化直通 |

**IOMMU 的安全动机**（值得单独记）：

在 IOMMU 出现前，设备发起 DMA 时给的是**裸物理地址**，总线不检查任何权限。后果：

- 一个有 bug 的驱动可能把数据写到内核的任意物理页
- 一个插进来的恶意设备（比如伪装成网卡的 FPGA）能读走整块物理内存
- 虚拟机直通设备时，客户机的设备能 DMA 到宿主机内存

IOMMU 把设备限制在**驱动明确映射给它的**那些物理页上，权限检查在硬件里做。

**对 pinned memory 的意义**：

驱动要向 DMA 引擎提交 buffer，就必须在 IOMMU 页表里建立 IOVA → PA 的映射。**这个映射一旦建立就必须持续有效**——IOMMU 不会因为物理页变了就自动更新，它只会拿已写好的翻译结果来用。

所以对 pageable 内存，驱动**没法建这个映射**（PA 会变）。它只有两个选择：pin 住再建映射，或者拿一块 pin 住的 staging buffer 中转。这就是那两条拷贝路径的硬件根源。

## 三层地址视图：谁能在哪一层合并？ #dma #iommu #arch

> **速查**
> - 三层地址：**VA**（用户态只见这个）/ **PA**（只有内核能查页表得到）/ **IOVA**（设备只见这个）
> - **用户态程序无法做物理合并**——物理地址在它的地址模型里根本不存在
> - 内核能合并：`get_user_pages()` 返回物理页数组 → 扫数组合并 → `dma_map_sg()`（**返回值可能小于输入**）
> - **有 IOMMU 时，"物理连续"这道墙对设备来说消失了**——IOMMU 把散页映射成连续 IOVA，设备看到一个连续段
> - **墙的位置变了**：从"物理内存碰巧连不连续"变成"IOMMU 用了多大的映射粒度"
> - 物理连续性的真实收益：**减少 IOMMU 页表项 + 减少引擎 IOTLB 项 + DRAM 行局部性**。**不减少事务追踪表**

### 正文

**谁能看到什么，决定谁有能力合并**：

| 角色 | 看到 | 能按物理连续性合并吗 |
|---|---|---|
| 用户态程序 | 只有 VA | ❌ **做不到**——物理地址对它不是可表达的量 |
| 内核 / 驱动 | VA 和 PA（能查页表） | ✅ 能 |
| IOMMU | PA ↔ IOVA 映射 | ✅ 能（方式不同，见下） |
| DMA 引擎 | 只有 IOVA / 请求流 | ✅ 能，但只能按**它收到的流**的连续性合并 |

**内核是怎么知道物理地址的**（不是猜的，是主动查）：

```c
get_user_pages(...)      /* 走页表，返回 struct page 数组 */
    ↓
每个 struct page → page_to_phys() → 物理地址
    ↓
扫数组，相邻物理地址连续的 → 合并
    ↓
dma_map_sg() 返回**可能变短了的** nents
```

> 经典驱动 bug：**必须用 `dma_map_sg()` 的返回值**，不能沿用传入的条目数。用错了会去读已经合并掉的条目，拿到垃圾地址。

**有 IOMMU 之后，这道墙对设备消失了**：

```
物理地址：  [PFN_a][PFN_x][PFN_a+1][PFN_z]   ← 打散
                ↓ IOMMU 页表映射
IOVA：      [ 0x8000 .................. 0x9000 ]  ← 设备看到的是一整段连续的
```

| 配置 | 设备看到的地址 | 墙在哪 | 谁负责合并 |
|---|---|---|---|
| 无 IOMMU | PA | **物理连续性边界** | 内核驱动（查页表后合并） |
| 有 IOMMU | IOVA | **IOMMU 映射边界** | IOMMU（把散页映射成连续 IOVA） |

**IOMMU 的映射粒度就是它自己页表的粒度**——IOMMU 也有 4 KB / 2 MB 之分。

**两个对称的优化**（同一个目的，作用在不同层）：

| 优化 | 在哪做 | 省掉什么 |
|---|---|---|
| 让物理内存连续 | 驱动分配 buffer 时（大页 / CMA / 预留连续区） | 省掉**无 IOMMU 时**的段数 |
| 让 IOMMU 用大页映射 | 驱动建 IOMMU 映射时 | 省掉**有 IOMMU 时**的映射表项和引擎 IOTLB 项 |

**物理连续性的收益清单（含"不是收益"的部分）**：

| 好处 | 成立条件 | 真的吗 |
|---|---|---|
| 减少描述符里的段数 | **只在无 IOMMU 时** | ✅ |
| 减少 IOMMU 页表项 | 有 IOMMU 时 | ✅ |
| 减少引擎 IOTLB 表项 | 有 IOMMU 且引擎缓存翻译 | ✅ |
| DRAM 行局部性 / bank 命中 | 总是 | ✅（但属于内存控制器，不是 DMA 引擎） |
| ~~减少 outstanding 表项~~ | — | ❌ **不是收益** |
| ~~减少 ROB~~ | — | ❌ **不是收益** |

**结论**：物理连续性的收益落在**翻译层**和**内存控制器**上，**从不落在事务追踪层**。因为追踪层按事务计数，而事务大小是协议（MPS）定死的，物理布局改变不了它。
