# SoC 架构与岗位知识背景

> 这份笔记来自两份 JD：一份是 **SoC 前端设计**（MMU/SMMU/NoC/低功耗 方向做深的模块 owner），
> 一份是 **SoC 架构师**（产品定义 + 子系统架构 + 前后端指导）。
>
> 目标不是罗列名词，而是给出每个知识域的**边界、必须能算的数、以及本库现有笔记的覆盖情况**。
> 读法：先看 §0 的映射表定位缺口，再按 §8 的顺序补。

## 两个 JD 差在哪？这其实是同一条 ladder 的两端 #soc #arch

> **速查**
> - 左边 JD 是**模块 owner**：产出是 RTL 和模块规格，深度优先
> - 右边 JD 是**芯片架构师**：产出是芯片规格、子系统边界、每个参数的预算值
> - 分水岭不是"会不会写 RTL"，是**能不能给参数定值并说清为什么是这个值**
> - 左边面试追问实现（几拍、缺页怎么走），右边追问取舍（为什么切三个电源域、为什么选这颗核）
> - 共同底座只有五块：处理器与虚拟化、互连、存储层级、低功耗、安全

### 正文

**① 两份 JD 的产出物对照**

| 维度 | JD1：SoC 模块 / 前端设计 | JD2：SoC 架构师 |
|---|---|---|
| 产出物 | 模块 RTL + 规格书 + 验证配合 | 芯片规格书 + 子系统架构 + 预算分配 |
| 决策粒度 | 模块内部：接口、流水线、时序 | 子系统 / 全芯片：选型、拓扑、功耗状态 |
| 时间尺度 | 周~月，tape-out 前 | 季度~年，从产品定义开始 |
| 深度 | 一个方向很深 | 每个子系统"够用"，但要知道边界在哪 |
| 对接 | 验证、后端、软件驱动 | 产品、算法、验证、后端、客户 |
| 失败代价 | 模块返工 | 流片失败 / 产品定位错误 |

**③ 产品定义这一步在产出什么**

链条是固定的：**需求 → 规格 → 架构 → 预算 → 接口契约**。架构师签的字主要落在"预算"这一环——
每个子系统分到多少算力、多少带宽、多少功耗、多少面积，加起来不能超过芯片级目标。

一个能当场验算的例子：整芯片目标 4 TOPS@INT8、功耗 5 W。若选能效 2 TOPS/W 的 NPU，
NPU 拿走 `4 ÷ 2 = 2 W`，剩 3 W 给 CPU、内存控制器、接口和 always-on 域。
如果实测只有 1.5 TOPS/W，NPU 要 `4 ÷ 1.5 ≈ 2.67 W`，多出来的 0.67 W 就得从别处扣——
要么砍算力、要么换工艺、要么降频。**这就是"架构决策"的实体：不是选型本身，是选型失败时谁让路。**

## 处理器虚拟化：VMSA / MMU / SMMU / ASID / nG 怎么串起来？ #arch #iommu #virtual-memory

> **速查**
> - **VMSA 是规范，MMU 是它的硬件实现**：页表长什么样、翻译怎么走、TLB 何时失效，都由 VMSA 定
> - MMU 服务 CPU（VA→PA）；SMMU 服务设备 DMA（IOVA→PA），同一套机制的两个使用者
> - 四个编号各管一层：**ASID 管进程、VMID 管虚拟机、StreamID 管设备、SubstreamID 管设备内的进程**
> - 有 ASID 后进程切换只写 TTBR + ASID，**不必整表 flush**；TLB 条目带 tag
> - **nG 位**决定一条映射是全局还是绑定当前 ASID——设错就是随机读到别人的内存

### 正文

**① VMSA 管什么、不管什么**

VMSA（Virtual Memory System Architecture）是 ARM 架构手册里定义地址翻译的那套规范：页表层级与格式、
4 KB / 2 MB / 1 GB 三种块大小、内存属性（normal / device、cacheable、shareable）、访问权限（AP、XN、PAN）、
以及 TLB 维护指令的语义。

**它不管的**：TLB 有多少项、几路组相联、用什么替换算法。这些属于微架构，实现自由。
所以"符合 VMSA"不等于"TLB 性能一样"——面试里这两层要分清。

**② 一次翻译怎么走**（AArch64，4 KB 页，48 位 VA）

```
VA[47:39] → L0 索引 →  L1 表
VA[38:30] → L1 索引
VA[29:21] → L2 索引
VA[20:12] → L3 索引
VA[11:0]  → 页内偏移
```

`TTBR0_EL1` 管低半区（用户态），`TTBR1_EL1` 管高半区（内核态）；`TCR_EL1` 配页表大小和 ASID 宽度。

验算一个：VA = `0x4000_0000`（1 GB）。`0x40000000 >> 30 = 1`，所以 **L0=0、L1=1、L2=0、L3=0**。

注意 L0 索引不是"恒为 0"：它由 `T0SZ` 决定。当 `T0SZ = 25` 时用户 VA 只有 `64 − 25 = 39` 位
（512 GB），L0 正好退化成只用一项；把 `T0SZ` 调小，用户空间就能一直用到 47 位。
**页表级数和 VA 宽度都是配置出来的，不是架构写死的**——这一句在面试里比记住 39 更值钱。

**③ 横向对比：MMU vs SMMU**

| | MMU | SMMU |
|---|---|---|
| 翻译谁 | CPU 核发出的 VA | 设备发出的地址（IOVA 或直通的 PA） |
| 谁是表主 | OS 内核（每进程一套） | 驱动 / hypervisor（每设备一套） |
| 翻译级数 | stage 1（虚拟化时加 stage 2） | stage 1 + stage 2 都支持 |
| 标识 | ASID（进程）、VMID（虚拟机） | StreamID（设备）、SubstreamID（设备内 PASID） |
| 失效手段 | `TLBI` 指令 | 命令队列里的 TLBI / ATC invalidate |
| 缺页 | CPU 异常，内核处理 | 设备侧几乎没有缺页路径，**映射必须先建好** |

最后一行是关键：设备不跑操作系统，处理不了缺页。所以驱动必须在提交 DMA **之前**把映射建好，
这正是 [[address-path#三层地址视图：谁能在哪一层合并？]] 里 pinned memory 存在的硬件根源。

**④ ASID 和 nG 到底在防什么**

场景：进程 A 和 B 都把 VA `0x4000_0000` 映射到各自的物理页。TLB 里可以有两条：
`{ASID=1, VA=0x40000000}` 和 `{ASID=2, VA=0x40000000}`。切换进程时写 `TTBR0_EL1`（ASID 在 [63:48]）
再 `ISB`，**不 flush**，命中各自的条目。

**反例**：如果页表项里 `nG=0`（全局映射），这条条目不属于任何 ASID。进程 B 切进来，
硬件按"全局 = 对谁都有效"命中 A 的翻译 → B 读到 A 的物理页。
症状是**随机数据损坏，且只在多进程同时存在时出现**，单进程测试永远抓不到。

失效指令的粒度也对得上：`TLBI VAE1IS, Xt` 按 VA+ASID 失效；`TLBI ASIDE1IS, Xt` 按整个 ASID 失效。
ASID 宽度由 `TCR_EL1.AS` 选 8 位或 16 位——8 位只有 256 个编号，进程多了要回收重用。

**⑤ SMMUv3 的结构与一个成本数字**

`StreamID → Stream Table Entry (STE)`；STE 里既可以挂 stage 2 页表基址（虚拟化直通），
也可以挂 stage 1 context 描述符表（按 SubstreamID 索引）。STE 的配置还能直接选 bypass / abort。

大页为什么重要，用数字说：**1 GB 缓冲区，4 KB 粒度要 `1 GB ÷ 4 KB = 262144` 条表项；
2 MB 粒度只要 `1 GB ÷ 2 MB = 512` 条。** SMMU 的翻译缓存（IOTLB）通常只有几百项，
4 KB 页根本装不下——这不是"性能差一点"，是**翻译缓存持续 miss，每次 DMA 都多一次访存**。

## TrustZone 怎么把系统切成两个世界？ #arch #security

> **速查**
> - TrustZone 是**访问控制**不是加密：一位 NS 把系统分成 Secure / Non-secure
> - 三层落地：CPU 的 EL3 + `SCR_EL3.NS`、总线的 `AxPROT[1]`、内存的 TZASC/TZMA 地址过滤
> - 它保护的是**资源**（内存、外设、中断），数据一旦进了 Non-secure 就归对方管
> - 安全启动是**信任链**：每一级验下一级签名，信任根在 BootROM / OTP 里的公钥
> - 车规里 **security（ISO/SAE 21434）和 functional safety（ISO 26262）是两件事**，别混

### 正文

**① 两个世界在哪几层分开**

| 层 | 机制 | 归属 |
|---|---|---|
| CPU | EL3 monitor + `SCR_EL3.NS`，决定 `ERET` 回哪个世界 | 硬件 + 固件（BL31） |
| 总线 | 每个 AXI 事务带 `AxPROT[1]`（NS 位） | 硬件 |
| 内存 | TZASC / TZMA 按地址段判归属，越界返回 DECERR | 硬件 + 启动时配置 |
| 中断 | GIC 分 Group 0（Secure）/ Group 1 Secure / Group 1 NS | 硬件 |
| DMA | SMMU 的 STE 里带 NS 配置，强制检查 | 硬件 + 驱动 |

**结论性的分工**：隔离的执行是硬件的，**划分和安全策略是软件在启动阶段写进寄存器的**。
"开了 TrustZone"只是打开了能力，策略配错等于没开。

**② 横向对比**

| | TrustZone | CCA / RME | x86 SGX | x86 TDX | RISC-V PMP |
|---|---|---|---|---|---|
| 世界数 | 2 | 4（Root / Realm / Secure / NS） | 进程 enclave | 机密 VM | 由软件划分 |
| 切换由谁管 | EL3 monitor | EL3 + RMM | 用户/内核指令 | VMM | M-mode |
| 主要场景 | TEE、DRM、安全启动 | 机密计算 | 小可信区 | 机密虚拟机 | 嵌入式隔离 |

CCA 多出来的 **Realm** 是给"机密虚拟机"用的，Root 世界管 Realm 的管理器（RMM）——
本质是把"hypervisor 自己不可信"这种情况也纳进来。面试里能说清这一层，比背名词有用。

**③ 安全启动链**

```
BootROM（信任根） → BL1 → BL2 → BL31（EL3 runtime） → BL33（U-Boot） → OS
```

每一级验下一级的签名，公钥哈希烧在 OTP / eFuse。BL31 常驻，负责 PSCI 和两个世界的切换。
**最常见的失败点**不是算法，是链路有旁路：调试口没关、熔丝没烧、验签失败后走了降级分支。

**④ 四个常见误解**

- "Secure 世界不能访问 Non-secure 内存" —— 通常**可以**，允不允许是配置项。
- "开了 TrustZone 就安全了" —— TEE 自己也可能有漏洞；隔离只是把攻击面变小。
- "安全岛 = Secure world" —— 不是。安全岛（safety island）是功能安全概念：主域失效时仍能维持
  基本功能（看门狗、跛行回家）的独立域，和 security 的信任边界无关。
- "设备 DMA 不受 TrustZone 管" —— 管，靠 SMMU；不配的话 Non-secure 侧的 DMA 能读走 Secure 内存。

## 总线、crossbar、NoC 怎么选？带宽怎么估？ #arch #noc #performance

> **速查**
> - 互连分三层：**协议**（事务怎么握手）、**拓扑**（谁连谁、几跳）、**IP**（厂商实现）
> - 从共享总线 → crossbar → NoC，换的是**并发度**，代价是面积和延迟
> - 带宽两步算：峰值 = 频率 × 位宽 ÷ 8，再乘有效系数 0.6~0.8
> - 需要的在途事务数 = 带宽 × 往返延迟（Little's law），不是拍脑袋定的
> - Coresight 不是总线，是调试/追踪子系统——JD 里把它和 NoC 并列，容易背错

### 正文

**① 三层各在定什么**

- **协议**：AXI4 五通道（AW / W / B / AR / R），读写分离，靠 `AxID` 乱序；AHB 两级流水；
  APB 简单低速，专供寄存器；CHI 包化并带一致性，用于多 cluster。
- **拓扑**：共享总线（一条线 + 仲裁）、crossbar（N×M 开关矩阵）、NoC（路由器 + 链路，多跳转发）。
- **IP**：ARM NIC-400/450（AMBA 互连）、CMN-700（CHI mesh）、Arteris FlexNoC（包交换 NoC）、
  Ncore（一致性互连）、Synopsys DesignWare AMBA fabric。

**② 横向对比**

| | 共享总线 | 全交叉 crossbar | NoC |
|---|---|---|---|
| 并发 | 同一时刻 1 对 | N×M 无阻塞（端口够时） | 多对并发，靠路由 |
| 面积 | O(N+M) | O(N×M)，16×16 就开始疼 | O(N) 个路由器 |
| 延迟 | 仲裁 + 传输 | 1 跳 | 跳数 × 每跳延迟 |
| 扩展性 | 差 | 到十几~几十个 master 失效 | 好，可加跳 |
| 典型用途 | APB 外设 | 中等规模 SoC 的主干 | 大 SoC / 多 cluster / chiplet |

判断标准不是"先进程度"，是**并发需求和端口数**：4 个 master、每个带宽都不高，crossbar 最划算；
64 个 master 还互不相干，crossbar 面积先爆，才轮到 NoC。

**③ 带宽怎么估（三步，都能验算）**

1. **峰值**：256 bit @ 1 GHz → `32 B/cycle × 1e9 = 32 GB/s`（单方向；AXI 读写通道独立，
   但 slave 端口带宽是共享的）。
2. **有效**：DDR 的读写切换、refresh、仲裁开销，工程上按 0.6~0.8。`32 × 0.7 ≈ 22 GB/s`。
3. **在途**：Little's law，`带宽 × 往返延迟`。`20 GB/s × 500 ns = 10 KB`，
   按 128 B 一笔 → **约 80 个 outstanding**。MSHR / 事务表少于这个数，就吃不满带宽。

**超卖的例子**：4 个 master 各要 8 GB/s，合计 32 GB/s；64-bit DDR4-3200 峰值
`3200 MT/s × 8 B = 25.6 GB/s`。缺口 6.4 GB/s。三个动作：加宽/加通道、提频、QoS 限流并接受降级。
**架构师要给出的就是"选哪个 + 各自代价"**，而不是"带宽不够"。

**④ 一致性和 QoS**

- 加速器一般走非一致端口：CPU 写完的数据，加速器看不到，必须由驱动做 cache flush / invalidate
  （或直接用 ACE/CHI 的一致性端口，代价是面积和布线）。
- QoS 靠 `AxQOS` 4 bit + 仲裁器加权。**实时流量（display、audio）要预留带宽**，
  只给高优先级不够——低优先级流量持续占满时，高优先级仍会被排队延迟拖垮。

## 低功耗：时钟门控、电源门控、DVFS 各打哪一项？UPF/VCLP 干什么？ #arch #low-power

> **速查**
> - 功耗 = 动态 `αCV²f` + 静态漏电；每种手段只打其中一项
> - **时钟门控**打 α，代价近零；**电源门控**打漏电，代价是隔离/保持/唤醒时间；**DVFS** 打 V²f
> - UPF（IEEE 1801）是**电源意图文件**，不是 RTL 的一部分
> - **VCLP** 做形式检查：UPF 声明的和 RTL 实现的是不是一回事
> - 电压、频率各降 20% → 动态功耗 `0.8² × 0.8 = 0.512`，约一半

### 正文

**① 四种手段的对照**

| 手段 | 省哪一项 | 代价 | 作用粒度 |
|---|---|---|---|
| 时钟门控 | 动态（α） | 一个 ICG 单元，几乎为零 | 寄存器 / 模块 |
| 电源门控 | 漏电 + 动态 | 隔离单元、保持寄存器、唤醒延迟 | 电源域 |
| DVFS | 动态（V²f） | PMIC、稳压、切换时序 | 电压域 |
| 多阈值（HVT/SVT/LVT） | 漏电 | 关键路径时序变差 | 标准单元 |

**② 三个必须说清的搭配**

- 电源门控必须配 **isolation**：域关断后输出浮空，跨域信号要钳到 0 或 1，否则下游输入不定，
  漏电甚至误触发。
- 跨电压域必须配 **level shifter**：A 域 1.0 V、B 域 0.8 V，A→B 直接连会让 B 的栅极过压。
- 门控的域里若要保住状态，必须配 **retention**：寄存器带影子锁存，关电前 save、上电后 restore。

**③ UPF 与 VCLP 的分工**

UPF 里就四类元素：power domain、isolation strategy、level shifter strategy、retention strategy，
再加一张 **PST**（power state table，声明哪些域的组合是合法状态）。

| | 谁在写 | 写什么 | 谁检查 |
|---|---|---|---|
| UPF | 架构 / 低功耗工程师 | 电源意图（域、隔离、电平、保持、状态表） | VCLP 形式检查 |
| RTL | 设计工程师 | 实际逻辑 | 仿真 + 综合 |

**VCLP 抓的是"两份描述不一致"**：漏了 isolation、level shifter 方向接反、retention 的
save/restore 信号悬空、PST 里有非法组合。最常见的来源是改了 RTL 没同步改 UPF。

**④ 算一遍 DVFS 的收益**

1.0 V / 1.0 GHz → 0.8 V / 0.8 GHz：

```
P_dyn ∝ V² × f = 0.8² × 0.8 = 0.512
```

动态功耗降到约一半。**收益主要来自 V²，降频只贡献一次方**——这就是为什么 DVFS 要成对调，
只降频不降压，功耗只线性降 20%，性能却同样掉 20%，不划算。

## 存储架构：cache、SRAM、DDR 的预算怎么分？ #arch #memory-hierarchy

> **速查**
> - 架构师定四个数：**容量、带宽、延迟、一致性**
> - cache 和 scratchpad 的分野是**谁做决定**：硬件（tag 比较）vs 软件（地址直接算）
> - 带宽永远不够，真正的设计动作是 **tiling + 片上复用**，不是换更快的 DRAM
> - 一致性要么硬件做（ACE/CHI），要么软件做（flush/invalidate），两头都不做就是随机读到旧数据
> - 64-bit DDR4-3200 峰值 25.6 GB/s；HBM3 单 stack 约 819 GB/s

### 正文

**① 层级与各自的角色**

| 层 | 典型容量 | 延迟量级 | 谁管理 |
|---|---|---|---|
| 寄存器 | KB | 0~1 拍 | 编译器 |
| L1 | 32~64 KB | 3~4 拍 | 硬件 |
| L2 | 256 KB~2 MB | 10~20 拍 | 硬件 |
| L3 / 系统 cache | 4~32 MB | 30~60 拍 | 硬件 |
| 片上 SRAM | 1~16 MB | 10~20 拍 | 软件 |
| DDR | GB | 60~100 ns | 控制器 |
| HBM | GB | 80~120 ns | 控制器 |

**② cache vs scratchpad**

| | cache | scratchpad |
|---|---|---|
| 命中判定 | tag 比较 | 地址直接算，无 tag |
| 谁决定放什么 | 硬件（替换算法） | 软件（显式 DMA） |
| 时延确定性 | 差（冲突、替换） | 好 |
| 面积效率 | 低（tag + 替换逻辑） | 高 |
| 典型使用者 | CPU / GPU | DSP / NPU |

判据是**负载的确定性**：通用负载猜不到下一步访存，只能靠 cache；固定数据流的算子知道下一步要什么，
scratchpad + 显式搬运更省面积也更好预测。

**③ 带宽预算：一个 NPU 的算术**

256×256 的脉动阵列 @ 1 GHz：每周期 65536 个 MAC，INT8 下 `65536 × 2 ops × 1e9 = 131 TOPS`。
如果每个 MAC 都要现取 1 B 权重 + 1 B 激活，是 `65536 × 2 B = 128 KB/cycle`，即 128 TB/s——不可能。

脉动阵列已经靠阵列内复用把输入压到每周期 512 个元素（左、上各 256 个），
INT8 下 `512 × 1 B = 512 B/cycle`，即 **512 GB/s @ 1 GHz**。仍然远超 DDR。

所以真正的动作是 **tiling**：让权重驻留片上，激活复用 R 次，则 DDR 侧带宽 `512 ÷ R GB/s`。
`R = 20` 时降到 25.6 GB/s，刚好是一条 64-bit DDR4-3200 的峰值。
**"带宽不够"这句话，在架构层面几乎等价于"tiling 的复用因子没算够"。**

**④ 一致性：硬件还是软件**

- 硬件一致（ACE/CHI）：cache line 状态机 + snoop 过滤，代价是面积和互连复杂度。
- 软件一致：驱动在 DMA 前后做 `dma_sync_single_for_device()` / `for_cpu()`；GPU 用 fence + cache 维护。
- **两头都不做**：设备读到 CPU 还压在 cache 里的旧值，症状是"偶尔跑错、加日志就好了"。

相关：[[cache-microarchitecture#Cache 的硬件结构：一次访问到底经过哪些部件？]] · [[computer-arch#数据流怎么选？复用因子怎么算？]]

## 子系统怎么切？架构文档写什么？ #soc #arch

> **速查**
> - 子系统 = 功能内聚的一组 IP + 本地互连 + 自己的时钟/电源域 + 寄存器接口
> - 切分依据五个：功能、带宽特征、时钟/电源域、安全等级、验证与复用边界
> - 架构文档顺序固定：需求 → 框图 → 地址映射 → 时钟复位 → 电源状态 → 性能预算 → 接口契约
> - 架构师的交付物是**约束和预算**，不是代码
> - 每个子系统都要能回答：占多少带宽、多少面积、几个电源状态、谁能访问它

### 正文

**① 七个子系统的看家指标**

| 子系统 | 典型 IP | 关键指标 | 常见坑 |
|---|---|---|---|
| CPU cluster | 核、L2、GIC、debug | 单核性能、一致性 | 中断路由、电源状态迁移 |
| GPU / NPU | 计算阵列、本地 SRAM、DMA | 峰值算力、能效、带宽 | 与 CPU 的一致性与同步 |
| 媒体 | ISP、VPU、显示 | 分辨率×帧率、端到端延迟 | 和计算单元抢 DDR 带宽 |
| 高速接口 | PCIe、USB、UFS、以太网、SerDes | 每 lane 速率、通道数 | PHY 面积、参考时钟、功耗 |
| 安全 | HSM、加解密引擎、OTP、TRNG | 算法吞吐、密钥生命周期 | 与功能安全的边界混淆 |
| 系统管理 | BootROM、PMU、时钟复位、thermal、看门狗 | 启动时间、待机功耗 | always-on 域面积和漏电 |
| 电源管理 | PMIC 接口、DVFS 表、电源状态机 | 状态迁移时间、纹波 | 跨域时序与隔离 |

**② 切分原则会打架，要看谁让步**

例子：ISP 和 VPU 都是视频通路，放一个子系统能共用时钟和 SRAM，省面积。
但 ISP 是实时的（不能降频），VPU 是尽力而为的（可以降频省电）——**功耗策略冲突**。
要么拆成两个电源域（同一子系统内），要么直接拆开。判据是"**能不能独立地改变它的频率/电压**"，
不是"功能像不像"。

**③ 架构文档的七页**

1. 需求：目标负载、性能/功耗/面积/成本指标、认证要求
2. 框图：子系统边界 + 互连拓扑
3. 地址映射：谁在哪个地址段，谁有权访问
4. 时钟与复位：几个时钟域、来源、跨域处理方式、复位树
5. 电源状态：状态机、每个状态的进出条件、保持内容
6. 性能预算：每个子系统的带宽/算力配额，加起来 ≤ 芯片级目标
7. 接口契约：寄存器规范、中断号、DMA 通道、软硬件分工

**④ 处理器选型不看峰值**

- CPU：性能核（如 Cortex-A78/X 系列）vs 能效核（A55）的大小核配比，取决于目标负载的并行度。
- GPU / NPU / DSP：GPU 通用并行、可编程性最好；NPU 固定数据流、能效最高；
  DSP 适合算子不规则、控制密集的信号处理。
- 判据是**目标负载下的能效 × 可编程性**，不是 TOPS 数字。TOPS 高但喂不饱（见 §5-③），等于没有。

## 后端与验证，架构师要懂到哪一步？ #arch

> **速查**
> - 三种验证手段是速度/容量的折中：仿真 < EMU < FPGA，调试可见性正好反过来
> - 面积估算三项：门数 × 单元面积 + SRAM macro + 布线开销（10~20%）
> - DFT 不是后端的事：scan/MBIST 影响时序、面积、时钟结构，架构阶段就要留余量
> - 架构师定的时钟/复位结构和电源域，直接决定 PD 能不能收敛
> - 量产后的问题大多回到"架构没留可观测性"：debug 寄存器、trace、性能计数器

### 正文

**① 三种验证手段**

| | RTL 仿真 | EMU（硬件仿真器） | FPGA 原型 |
|---|---|---|---|
| 速度 | 10²~10⁴ Hz（看规模，门级更低） | 0.5~5 MHz | 10~50 MHz |
| 容量 | 小，单模块~子系统 | 大，可全芯片 | 中，要切分 |
| 调试可见性 | 全信号可见 | 较好 | 差 |
| 主要用途 | 模块验证、回归 | 全芯片启动、软件 bring-up | 系统联调、真实接口 |

顺序通常是：模块仿真 → 子系统 EMU → 全芯片 FPGA/EMU → 硅后 validation。
**不是替代关系，是同一份 RTL 在不同保真度下的复用。**

**② 架构师要能给的四组数**

- **面积**：`Σ(门数 × 单元面积) + Σ SRAM macro 面积 + 布线开销(10~20%)`。
- **功耗密度**：热点在哪、floorplan 怎么摆才不撞 thermal 上限。
- **时钟**：几个域、跨域用异步 FIFO 还是握手、时钟树深度对 skew 的影响。
- **DFT**：scan 插入后的时序余量、MBIST 对 SRAM 的额外端口与面积。

**③ 三类典型返工**

| 问题 | 根因 | 代价 |
|---|---|---|
| 后期加 CDC 同步器 | 时钟域切错 | 面积 + 延迟，可能改接口 |
| 隔离单元太多面积爆炸 | 电源域切太细 | 回退重划电源域 |
| 硅后定位不了问题 | 没留 debug 通路 | 只能改版重流片 |

## 缺口清单与补齐顺序 #soc #arch

> **速查**
> - P0（两个 JD 都点名 + 本库零覆盖）：SMMU/VMSA 细节、TrustZone、NoC 拓扑与带宽、UPF
> - P1（有碎片、要串成体系）：存储预算、低功耗手段、后端流程
> - P2（靠项目讲，不用专门背）：子系统划分、产品定义
> - 顺序：SMMU + TrustZone → NoC → UPF → 车规标准
> - 每个主题的过关标准：**能画图 + 能算数 + 能说清为什么不是另一个选择**

### 正文

| 优先级 | 主题 | 现有素材 | 下一步 | 过关标准 |
|---|---|---|---|---|
| P0 | VMSA / SMMU / ASID / nG | [[address-path]]、[[pcie-iommu]] | 补页表格式与 TLBI 粒度 | 能画两级翻译并算出表项数 |
| P0 | TrustZone / 安全启动 | 无 | 补 NS 位三层链路与启动链 | 能说清一个 DMA 如何被拦住 |
| P0 | NoC 拓扑与带宽预算 | [[c2c-crosscard]] | 补 crossbar vs NoC 判据 | 能现场算带宽和 outstanding |
| P0 | UPF / 低功耗 | 无 | 补四类元素与 PST | 能指出一段 UPF 缺了什么 |
| P1 | 存储层级与预算 | [[cache-microarchitecture]] | 补 tiling 带宽推导 | 能算 NPU 的复用因子 |
| P1 | 后端与验证 | 零散 | 补三种验证手段对比 | 能估面积、说清 DFT 影响 |
| P2 | 子系统与产品定义 | [[huawei-mpu]] | 用项目讲 | 能画一张子系统边界图 |

**车规补充**（JD1 优先项 2）：AEC-Q100 是器件可靠性认证，ISO 26262 是功能安全（ASIL A~D），
ISO/SAE 21434 是网络安全。三者管的东西不同，面试里说混了会被追问。
