# 性能建模方法

## 性能建模有哪几种粒度？周期级一定要倒序执行吗？ #arch

> **速查**
> - 五层粒度：解析 / trace-driven / 事务级（LT·AT）/ 周期近似 / 周期精确
> - 越往上越快、越早能用；越往下越准、越贵。**建模目的是回答问题，不是复刻 RTL**
> - 周期级的硬要求是**每个周期都保持状态转移与时序关系**，不是"每拍调用一次函数"
> - 倒序执行只是为了不让前级提前更新状态；**current/next 分离 + 统一提交**可以替代，且与顺序无关
> - TLM-2.0 只标准化 LT / AT，**没有规定 cycle-accurate 风格**

### 正文

**① 五层粒度：各自回答什么问题**

| 层次 | 靠什么建模 | 速度 | 能回答 | 典型用途 |
|---|---|---|---|---|
| 解析模型 | 公式：roofline、排队论、带宽预算 | 极快 | 上限、趋势、设计空间 | 早期架构探索 |
| Trace-driven | 真实访存/指令 trace + 缓存与带宽模型 | 快 | 访存行为、瓶颈在哪 | 有 trace 的中期 |
| 事务级 LT | `b_transport` + quantum | 快 | 功能、软件 bring-up、粗略性能 | 软件先行 |
| 事务级 AT | `nb_transport` 四相 | 中 | 流水、争用、乱序 | 性能分析 |
| 周期近似 | 周期级时序 + 简化资源模型 | 较慢 | 吞吐、利用率、瓶颈 | 微架构评估 |
| 周期精确 | 每周期状态转移 | 慢 | 周期级正确性 | RTL 前的 golden model |

**判据不是"谁更准"，是"你现在要回答哪个问题"**。早期没有 RTL 细节，周期精确模型根本建不出来；
等 RTL 有了，解析模型又回答不了"这一拍对不对"。

**② 横向对比：为什么不能一步到位用周期精确**

| | 抽象高（解析 / LT） | 抽象低（周期精确） |
|---|---|---|
| 建模成本 | 低，几天到几周 | 高，数月 |
| 仿真速度 | 快（LT 比 RTL 快几个数量级） | 慢 |
| 可信度 | 只能给趋势/上限 | 能逐拍对拍 |
| 变更成本 | 改参数即可 | 改结构要重写 |
| 什么时候用 | 设计空间探索、软件先行 | 微架构验证、性能签名 |

一个解析模型的例子：峰值 100 TOPS、带宽 1 TB/s、算术强度 100 ops/B。
带宽能支撑的算力 = `1e12 B/s × 100 ops/B = 1e14 ops/s = 100 TOPS`——正好卡在平衡点。
强度掉到 50，带宽就只能喂出 50 TOPS。**这种结论不需要跑仿真，但它也永远不会告诉你"第 7 拍握手错了"**。

**③ 周期级建模：倒序执行到底在解决什么**

周期级的硬要求是：**每个周期结束时，所有状态都等于"本周期输入 + 上周期状态"算出来的值**。
难点在于同一周期内的模块互相依赖：

```
A 的组合输出 → B 的输入（同一周期内）
```

- **正序执行**（A 先算、立即写）：B 读到 A 本周期的新值 → 相当于 A 的组合路径在本周期就传到了 B，
  少了一级寄存器，周期语义错了。
- **倒序执行**（B 先算、A 后算）：B 读到 A 上一周期末的值 → 边界正确。这就是倒序的全部目的。

但倒序**不是唯一解**，而且它把正确性绑在调用顺序上。更明确的做法是
**current-state / next-state 分离**：

1. 所有模块只读 `current` 状态；
2. 计算结果只写 `next` 状态；
3. 周期末统一 `current ← next`。

| | 倒序执行 | current / next 两阶段 |
|---|---|---|
| 正确性依据 | 调用顺序（隐式约定） | 状态分离（显式） |
| 换顺序会不会错 | 会 | 不会 |
| 可读性 | 要记住"从后往前" | 一眼看出读写的是哪份状态 |
| 代价 | 无额外存储 | 需要两份状态（或一个 delta） |

> 这和 SystemC 内核的 **evaluate / update** 是同一件事：求值阶段大家读旧值，更新阶段统一提交。
> 所以"用 delta cycle 写周期模型"本质上就是 current/next 分离，不需要倒序。

**④ TLM-2.0 的边界**

TLM-2.0 标准化的是 **LT 和 AT 两种事务传输风格**（`b_transport`、`nb_transport` 四相、generic payload、DMI）。
它**没有规定** cycle-accurate 建模该长什么样——没有标准的周期接口、没有规定的状态提交方式。
所以"TLM 做周期精确"是团队自定风格：有人用 AT 的四相近似，有人自己加周期计数器和 current/next 状态。

**⑤ 怎么选：问题决定粒度**

| 你现在要回答 | 选 |
|---|---|
| 这个架构理论上限多少？ | 解析模型（roofline / 排队论） |
| 真实负载下瓶颈在哪？ | trace-driven |
| 软件能不能跑起来？ | LT |
| 两次访问能不能重叠？ | AT |
| 这个流水线每拍对不对？ | 周期近似 → 周期精确 |

一个 trace-driven 的算例：16 个 MSHR、访存延迟 100 ns、每笔 64 B。
并发上限 = `16 ÷ 100 ns = 1.6e8 笔/秒`，带宽上限 = `1.6e8 × 64 B = 10.24 GB/s`。
**这个数字用解析式就能算，不需要仿真**——但只要你想知道"MSHR 满了以后谁被阻塞"，就必须往下走一层。
