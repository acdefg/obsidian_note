# SystemC 仿真内核

## delta cycle 是什么？为什么 write() 之后读不到新值？ #arch

> **速查**
> - SystemC 是**离散事件仿真**（DES）：只在事件发生时处理，时间直接跳到下一个事件
> - 一个 delta = **求值（evaluate）+ 更新（update）**，**不推进仿真时间**
> - `write()` 只登记"待更新"；信号在 update 阶段才提交，同一 delta 内大家读到的是旧值
> - 值变化在 update 阶段 `notify` 事件，敏感进程被排进下一个 delta 的求值队列
> - 所有 delta 跑完、可运行队列为空，时间才推进到下一个定时事件

### 正文

**① 三个层次：时间、delta、两阶段**

SystemC 的调度器按三个层次工作：

| 层次 | 是什么 | 什么时候结束 |
|---|---|---|
| 仿真时间 | 模型里的"现在是几 ns" | 只在没有待处理活动时前进 |
| delta cycle | 零时间的因果链：同一个时间点内的连锁反应 | 可运行队列和 delta 队列都空了 |
| 求值 / 更新 | 每个 delta 内的两个阶段 | 先跑完所有进程，再统一提交写 |

`SC_METHOD` 和 `SC_THREAD` 都是被"事件"唤醒的进程；敏感列表决定它们听哪个事件。

**把一轮调度展开，就是四步**：

1. **Evaluate（求值）** —— 调度所有可运行的进程（`SC_METHOD` / `SC_THREAD`），它们读信号、算结果、发起写入。
2. **Update（更新）** —— 提交 `sc_signal` 等通信对象的待更新值；值发生变化时产生事件。
3. **Delta 循环** —— 如果 update 产生了新事件，回到第 1 步；直到当前时间点没有待处理的增量活动。
4. **推进时间** —— 当前时间点没有可执行活动了，内核跳到下一个定时事件（timed event）。

> ⚠️ **最常见的误解**：SystemC **不是**"每执行一个进程就推进一个时钟周期"。
> 同一个仿真时间点可以跑多个进程、跑多轮 delta，而**时间纹丝不动**——时间只在第 4 步前进。
> 刚从 RTL testbench 转过来的人最容易在这里画错时序图。

**② 为什么必须分两阶段**

如果 `write()` 立即生效，仿真结果会依赖**进程执行顺序**：

- A 先跑 → B 看到新值；
- B 先跑 → B 看到旧值。

同一份模型、同一个输入，换个调度顺序结果就变——模型不可复现，验证也就失去意义。

两阶段解决的就是这件事：**evaluate 阶段所有进程读同一份快照，update 阶段统一提交**。
这就是常说的 **read-old / write-new** 语义。代价是写完之后不能立刻读到，多了一个 delta 的延迟。

**③ 手推一个 delta：两个进程、一个信号**

模型：`sc_signal<int> sig` 初值 0；`SC_METHOD` A 写 `sig=1`，`SC_METHOD` B 读 `sig`；两者都对 `sig` 敏感。

| 阶段 | A | B | `sig` 的值 |
|---|---|---|---|
| delta 0 · evaluate | `write(1)` —— 只登记"待更新" | 读 `sig`，得到 0 | 0 |
| delta 0 · update | — | — | 提交为 1，并 `notify` |
| delta 1 · evaluate | 被事件唤醒 | 被事件唤醒，读 `sig`，得到 1 | 1 |
| delta 1 · update | — | — | 无变化 |

输出是 `0` 然后 `1`，而**两行之间仿真时间没有前进一步**——这正是 delta cycle 的含义：
零时间，但因果要分先后。

**④ 横向对比：三种仿真时间模型**

| | SystemC DES | RTL 事件仿真 | 周期精确模型 |
|---|---|---|---|
| 时间推进方式 | 事件 + delta | 事件 + delta | 每个时钟周期固定推进 |
| 建模对象 | 事务 / 行为 / 架构 | 门与寄存器 | 周期级流水 |
| 速度 | 快（通常比 RTL 快几个数量级） | 慢 | 最快 |
| 能回答的问题 | 功能、性能趋势、软硬件划分 | 时序是否正确 | 吞吐、利用率、瓶颈 |

> 表里说的是**典型用法**：SystemC 也能写周期精确模型（`SC_CTHREAD`），RTL 也能跑行为级。
> 真正的分界不是语言，是"时间被建模到多细"。

**⑤ 怎么用：API 语义与四个坑**

| API | 语义 | 什么时候用 |
|---|---|---|
| `SC_METHOD` | 敏感列表触发，跑完返回，**不能 `wait()`** | 组合逻辑、寄存器更新 |
| `SC_THREAD` | 可以 `wait()`，挂起后由事件唤醒 | 行为建模、激励生成 |
| `sc_signal` | **值变化时**才 `notify` | 普通信号 |
| `sc_buffer` | **每次 `write()` 都 `notify`**，即使值没变 | 需要"每拍触发"的握手/时钟类信号 |

通知的时间点也分三种：

- `notify(SC_ZERO_TIME)` → 下一个 delta（零时间，但延后一个 delta）；
- `notify(t)` → 定时事件，到 t 才触发；
- `notify()`（无参）→ 立即通知，容易和 delta 混淆，初学先别用。

**四个坑**：

1. `write()` 后立刻 `read()` 同一个信号 → 读到旧值（update 才提交）。
2. 用 `sc_signal` 当"每拍事件"：值不变时**不触发**，敏感进程根本不会醒 → 换 `sc_buffer` 或 `clock.posedge_event()`。
3. 零延迟组合环（A 的输出驱动 B，B 的输出又驱动 A，中间没有时钟）→ delta 无限循环，仿真卡死。
4. 一个 `sc_signal` 挂两个驱动 → 报 multiple writer 错误；需要多驱动时用 `sc_buffer` 或在模型层做仲裁。
