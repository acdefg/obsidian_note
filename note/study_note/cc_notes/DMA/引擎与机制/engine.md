# DMA 引擎

## SGL（Scatter-Gather List）是什么？ #dma #sgl

> **速查**
> - 描述符数组，每项一对 `{地址, 长度}`，让设备按顺序把多段拼成一条连续的数据流
> - 它解除的是**物理连续**要求：没有 SGL，一次传输必须落在一块物理连续内存上
> - **支持 SGL 是硬件能力**——芯片里必须有一个能解析描述符列表的状态机
> - **使用 SGL 是软件工作**——驱动负责把物理页切成段、按硬件规定的格式填进数组
> - SGL 和 IOMMU 在功能上重叠（IOMMU 也能把散页映射成连续 IOVA），是**替代关系**不是配套关系
> - 因为 SGL/IOMMU 已经解决了连续性，**pin 才只需要保证"页不动"，不需要保证"页连续"**

### 正文

**结构**：

```
无 SGL：  DMA 引擎 ← { addr: 0x1000, len: 1048576 }
                    要求这 1MB 在物理上完全连续

有 SGL：  DMA 引擎 ← 描述符数组：
          ┌─────────────────────────────────┐
          │ desc[0]  addr=0x1A000  len=4096 │
          │ desc[1]  addr=0x7F3000 len=4096 │   ← 物理上完全不挨着
          │ desc[2]  addr=0x21000  len=2048 │
          └─────────────────────────────────┘
          硬件依次读这些区间，拼成一条字节流交给上层
```

**三层归属**（这三层缺一不可）：

| 层 | 内容 | 归属 |
|---|---|---|
| ① 描述符格式 | 每个描述符多少字节、字段怎么排、类型怎么编码 | **硬件定义**——写在 NVMe 这类规范里，软件必须照着填 |
| ② 构造描述符列表 | 遍历 buffer 的物理页 → 合并相邻页 → 按格式填数组 → 把数组地址写进硬件寄存器 | **纯软件**——驱动的工作 |
| ③ 遍历列表、发起内存事务 | 读 desc[0] → 发 PCIe 读请求 → 收数据 → 读 desc[1] → …… | **纯硬件**——DMA 引擎里的状态机 |

**为什么"支持"必须是硬件先行**：只支持单段传输的 DMA 引擎，你给它描述符数组的地址，它**不会去解析数组**——它会把你给的地址当成数据地址直接读，结果是数据全错。这不是"没优化"，是"用不了"。

**和 IOMMU 的关系**（不直观，容易搞混）：

IOMMU 其实能做到同一件事——驱动可以在 IOMMU 页表里把散落的物理页映射成**一段连续的 IOVA**，设备只要看到一个连续地址就行，根本不需要 SGL。两者是替代关系：

| 方案 | 做法 | 代价 |
|---|---|---|
| 纯 SGL | 设备自己处理散页 | 设备硬件更复杂，每个描述符有解析开销 |
| 纯 IOMMU | 驱动建映射，设备只见连续 IOVA | 每次翻译多一层查表延迟；映射建立有成本 |

那为什么现代设备**都还是支持 SGL**？因为：

- **IOMMU 可以被关闭或以直通模式运行**——很多 HPC/GPU 场景为了省掉翻译延迟（每次要走 IOTLB，miss 时要去内存取 IOMMU 页表）会关掉它。这时设备必须自己处理散页
- 不是所有平台都有 IOMMU（嵌入式、老平台）
- 单次传输可能超出 IOMMU 映射能覆盖的范围

**另一层**：**"页是散的"这件事本身是软件造成的**——是 OS 的物理页分配器决定的不连续。SGL 不是主动选择，是对这个现实的适应。如果 OS 恰好给了连续页，SGL 就退化成单描述符。

## 现代 DMA 引擎有哪些技术？ #dma #arch

> **速查**
> - 六条分类轴：**编程模型 / 地址翻译 / 数据路径 / 完成通知 / 引擎位置与能力 / 传输中是否变形**
> - 编程模型演进：单段 → SGL → 链式描述符 → **描述符环**（现代高速设备主流，NVMe 和网卡都是）
> - 地址翻译演进：裸物理地址 → IOMMU → **ATS**（设备自带 ATC 缓存翻译结果）→ PRI → PASID+SVA
> - 完成通知：轮询 / 中断 / **MSI-X**（最多 2048 向量，支持多队列绑核）/ 中断合并（延迟换 CPU 开销）
> - 数据路径：H2D·D2H / **P2P**（设备↔设备不过主机内存）/ M2M
> - 演进主线一句话：**让硬件承担更多原本由软件做的决定**

### 正文

**轴一 · 编程模型**（最核心，决定引擎复杂度）

| 代际 | 模型 | 归属 |
|---|---|---|
| 1 | 单段 DMA——一对 `{地址, 长度}` 写进寄存器 | 【硬】地址/长度寄存器 + 计数器状态机<br>【软】写寄存器配置 |
| 2 | SGL——描述符数组 | 【硬】描述符解析前端<br>【软】切段填数组 |
| 3 | 链式描述符——每项带指向下一项的指针 | 【硬】解析器支持指针跳转<br>【软】可增量追加段 |
| 4 | **描述符环**——固定长度环形数组在主机内存，生产者/消费者各持一个索引 | 【硬】引擎维护消费指针<br>【软】维护生产指针、批量提交 |

**描述符环为什么是现代主流**：它是固定大小的连续内存，对缓存友好；单生产者单消费者，一个方向只写一个索引，**不需要锁**；批量提交摊薄了每次传输的寄存器配置成本。NVMe 的提交/完成队列、网卡的 TX/RX ring 都是它。

**轴二 · 地址翻译**

| 机制 | 做什么 | 归属 |
|---|---|---|
| 裸物理地址 | 设备直接收 PA，总线不检查权限 | 【硬】无翻译电路<br>【软】驱动必须 pin |
| IOMMU | 设备用 IOVA，IOMMU 翻译 | 【硬】IOMMU 翻译电路 + IOTLB<br>【软】驱动建 IOMMU 页表 |
| **ATS** | 设备有**自己的 TLB**（叫 ATC，Address Translation Cache），主动向 IOMMU 请求翻译并缓存 | 【硬】设备侧 ATC + IOMMU 应答，PCIe 层协议 |
| **PRI** | 设备遇到未映射页时主动请求 IOMMU 去取 | 【硬】需两端都支持；延迟微秒级 |
| **PASID + SVA** | 一次 PCIe 事务带 PASID（20 位进程地址空间 ID），让设备同时使用多个进程各自的页表 | 【硬】PASID 字段 + 设备侧多上下文<br>【软】内核分配 PASID |

**ATS 的工程价值最大**：没有它，每次 DMA 访问都要走 IOMMU 翻译，IOTLB miss 就要去内存取 IOMMU 页表。有了 ATS，设备把翻译结果缓存在自己芯片里，后续访问本地命中。

**PASID + SVA（Shared Virtual Addressing）** 是"设备直接用进程虚拟地址"的基础，也是用户态直接操作设备（DPDK、SPDK、GPU 共享虚拟内存）的底层支持。

**轴三 · 数据路径**

| 路径 | 说明 | 关键约束 |
|---|---|---|
| H2D / D2H | 主机内存 ↔ 设备本地内存（如 GPU 显存） | 走 PCIe，带宽瓶颈 |
| **P2P** | 设备 ↔ 设备，不经过主机内存 | 两者必须挂在同一 PCIe 层级（同 root complex 或同 switch）；IOMMU 要配好或旁路 |
| M2M | 内存 ↔ 内存，用 DMA 引擎代替 CPU 拷 | 释放 CPU，但带宽通常不如 CPU 直接拷 |

P2P 的两个实例：**GPUDirect RDMA**（网卡直接读写 GPU 显存）、**GPUDirect Storage**（NVMe 直接读写显存）。

**轴四 · 完成通知**

| 机制 | 说明 | 归属 |
|---|---|---|
| 轮询 | 软件自旋读内存位置 | 【软】纯策略 |
| 中断 | 设备拉中断线 | 【硬】设备发<br>【软】内核处理 |
| **MSI-X** | 消息信号中断的扩展版，最多 2048 个向量 | 【硬】设备侧多向量<br>【软】内核绑定到不同 CPU 核 |
| 中断合并 | 等 N µs 或攒够 M 个事件再发一次中断 | 【硬】设备内定时器/计数器<br>【软】配置阈值 |

MSI-X 的意义是**多队列**：每个队列绑一个中断向量、一个 CPU 核——网卡多队列、NVMe 多队列都靠它做 CPU 亲和性。

与它配对的是**门铃（doorbell）**：反方向，软件写寄存器告诉设备"有新任务"。这是 MMIO 写，很贵，所以才有**门铃批处理**。

**轴五 · 引擎位置与能力**

- **集中式 DMA 控制器**——一个系统共享的通用引擎，嵌入式常见（ARM PL330 等）
- **每设备独立引擎**——GPU 有多个拷贝引擎（AMD 叫 SDMA，NVIDIA 叫 CE），可并行跑多方向传输
- **SmartNIC / DPU**——网卡自己能跑代码，在 DMA 通路上做变换（加解密、压缩）。NVIDIA BlueField、AMD Pensando
- **智能 DMA**——引擎本身能变形数据，见轴六

**轴六 · 传输中是否变形**（近十年变化最大）

线性拷贝 → 跨步/多维（描述符带步长和维度，显示控制器和 ISP 需要）→ 在线加密（AES-XTS 在 DMA 通路上）→ 在线压缩 → 格式转换（YUV→RGB、数据类型转换）

**TMA——这条轴上的当前顶点**

TMA（Tensor Memory Accelerator，Hopper 引入）超出了传统 SGL 的能力范围：

- 用**张量映射**（tensor map）描述数据：形状、步长、元素类型、**swizzle 模式**
- 硬件负责**地址生成**、**边界处理**（越界自动填零）、**swizzling**（重排布局以避免 shared memory 的 bank conflict）
- 一次描述符搬一个多维 tile，不是一维字节流
- 完成走 **mbarrier**（异步屏障，TMA 完成时硬件对屏障做一次到达操作），不需要软件轮询
- 支持**多播**：一次 TMA 把同一份数据写进同一 cluster 内多个 CTA 的 shared memory

**和 SGL 的关键差别**：SGL 描述符是"从 A 读 N 字节"；TMA 张量映射是"这是一个 128×64 的 tile，元素 16 位，行步长 512 字节，按 128 字节 swizzle"——**硬件要做的地址生成复杂了一个量级**。

## DMA 引擎实际在做什么？ #dma #arch

> **速查**
> - 链路控制器接走了"快且可靠"，引擎剩下的接口确实简单（发事务描述 / 收完成信号）
> - 但引擎的问题不是"怎么和链路说话"，是**"把软件意图翻译成正确的事务序列"**
> - 八项工作：① 描述符解析 + 地址生成 ② 粒度翻译（分割/合并）③ 排序与依赖 ④ **完成语义** ⑤ 地址翻译 ⑥ **一致性维护** ⑦ 仲裁与 QoS ⑧ 错误处理
> - **最难的三条**：完成语义（"发出"≠"可见"）、一致性维护（读前 flush / 写后 invalidate，且必须与传输严格定序）、地址翻译（中途 miss 不能停）
> - 判断"某层是否简单"的方法：**看它需不需要知道软件语义**。链路控制器不需要，引擎必须知道——**需要理解语义的那一层永远不简单**
> - 一句话分工：**链路控制器做"快且可靠"，DMA 引擎做"对"**

### 正文

**八项工作，按难度从低到高**：

**① 描述符解析 + 地址生成**——线性拷贝确实简单（`addr, addr+len`）。**但 TMA 的地址生成器是另一回事**：形状 128×64、元素 16 位、行步长 512 字节、128 字节 swizzle —— 硬件要生成**多维嵌套循环 + 步长算术 + swizzle 重排 + 越界填充**。

**② 粒度翻译**——描述符说"拷 1 MB"，链路要包。中间要切分 + 合并（见下一条）。

**③ 排序与依赖**——描述符环必须按序完成或明确告诉软件没按序；传输之间可能有依赖；**不同目标内存的排序规则不一样**（设备内存 / 主机内存 / 对端内存，三套规则）。

**④ 完成语义——"完成"是哪个时刻？** 三个不同的答案：

```
① 最后一个字节交给链路控制器了吗？
② 对端 ACK 了吗？
③ 数据在目标内存里**可见**了吗？
```

`cudaMemcpyAsync` + stream 的语义要求的是 ③。**"发出去了"和"可见了"中间隔着好几个阶段。**

**⑤ 地址翻译**——虚拟地址要查 IOTLB 或走页表；**传输中途 translation miss 不能停**，必须有处理路径。

**⑥ 一致性维护——复杂度的最大来源**：

- **读源之前**：源数据可能脏在 SM 的 L1/L2 里没落到 DRAM，要不要先 flush？
- **写目标之后**：对端的读者什么时候能看到？要不要让对端 invalidate cache？
- 在**非一致**内存域之间搬运时，这些操作必需，而且**必须和传输严格定序**——早一步读到旧数据，晚一步多一次 flush

**⑦ 仲裁与 QoS**——多队列/多流/多客户端抢同一个引擎。

**⑧ 错误处理**——翻译失败、ECC 错、链路报错，怎么报告和恢复。

**分工的本质**：

| | 链路控制器 | DMA 引擎 |
|---|---|---|
| 时间尺度 | flit 周期（亚纳秒） | 软件时间尺度（µs–ms） |
| 回答的问题 | "这个包送到了吗？" | "软件到底想要什么？" |
| 输入 | 一个事务描述 | 一个描述符（可能多维、带依赖、跨地址空间） |
| 核心难点 | **快且可靠** | **对** |

**这两类问题正交，所以能分两层——但都不简单。**

**从"简单版"到"真实版"的差距，就是这道题的答案**：

```
简单版（嵌入式单段 DMA）：
  描述符 FIFO → 地址生成（几个加法器）→ 事务队列 → 链路接口

真实版（GPU DMA / TMA）：
  描述符/张量映射 → 多维地址生成 + swizzle → 边界处理
                        ↓
                一致性操作生成（flush/invalidate）
                        ↓
                分割 / 合并 / 顺序管理
                        ↓
                翻译（IOTLB + miss 处理）→ QoS 仲裁 → 链路接口
                        ↓
                完成追踪（到"可见"而非"已发"）→ mbarrier / 事件
```

## 分割、合并与顺序管理 #dma #arch

> **速查**
> - 三者是同一件事的三个面，都在处理：**软件的粒度 ≠ 内存的粒度 ≠ 链路的粒度**
> - **分割**：从描述符到 flit 要穿过五层边界（虚拟页 / 物理段 / MPS / 目标空间 / 一致性粒度），**难点是多层切点不一致**
> - **合并**：把小于**下游最大单元**的单元攒大。`write-combining` 攒到 cache line，DMA 攒到 MPS
> - **合并的收益上限 = 下游最大单元 ÷ 上游最小单元**。上游已经等于下游时，收益为零
> - ⚠️ **分层计数判据**：某个优化能否减少某个结构，取决于**那个结构按哪一层的单元计数**。ROB/追踪表按"在飞字节数 ÷ 事务大小"计 → 描述符合并**不能**减少它
> - **顺序管理四层**：描述符之间 / 传输内部 / 传输之间（依赖 → 屏障）/ 内存模型顺序（不同目标空间规则不同）
> - **屏障会排空流水**，吃掉前面所有合并与乱序的收益——屏障要尽量少

### 正文

**分割：五层边界，切点规则各不同**

```
描述符          1 MB（虚拟连续）
    ↓  切点：虚拟页边界
翻译单元        256 个 4 KB 页 —— 每页一次独立翻译
    ↓  切点：物理连续性
物理段          假设合并成 64 段
    ↓  切点：链路 MPS
链路包          ≤ 4096 字节（PCIe 的 MPS，Max Payload Size）
    ↓  切点：物理层帧格式
flit
```

| 层 | 为什么在这切 |
|---|---|
| 虚拟页边界 | 翻译是**按页**做的，跨页就换映射 |
| 物理连续性 | 物理页散落，每段要独立寻址 |
| MPS 边界 | 链路协议规定的单包最大负载 |
| 目标空间边界 | 从 peer A 换到 peer B，路由信息要变 |
| 一致性粒度 | flush/invalidate 按 cache line 或按页做 |

**难点不是切开，是多层切点不一致还得同时满足**：按页要切 256 次，按物理连续可能剩 64 段，按 MPS 又切成 4096 个包。三个数字必须同时对上，切点位置互相不对齐。

**合并：目的是凑到下游最大单元**

| 场景 | 合并到什么粒度 | 收益 |
|---|---|---|
| CPU write-combining buffer | **cache line（64 字节）** | 小 store 合成整行，减少总线事务 |
| DMA 引擎 | **MPS（≤4096 字节）** | 小于 MPS 的请求合成满包，减少包头和信用操作 |
| 内存控制器 | DRAM burst / row | 提高行局部性 |

**合并的上限就是下游最大单元**。把 64 字节请求合成 4096 字节包 → 有收益；把 4096 字节包再合成 1 MB → **没有收益**（链路还是要切成 4096 字节的包）。

**合并撞得到的四堵墙**（判据：**某个属性在边界处发生变化**）：

| 墙 | 边界处变了什么 |
|---|---|
| 页 | **翻译映射**变了 |
| 域 | **一致性规则**变了 |
| 目标 | **路由信息**变了 |
| QoS | **优先级**变了 |

**⚠️ 分层计数判据（这是判断优化有效性的通用工具）**：

| 层 | 单元由什么决定 | 合并能减少它吗 |
|---|---|---|
| 描述符 | 地址空间里的连续段 | ✅ 能（靠 VA/IOVA 连续，**不一定靠物理连续**） |
| **事务 / 包** | **链路 MPS** | ❌ **不能**——除非原请求本来就小于 MPS |
| **ROB / 追踪表** | **在飞字节数 ÷ 事务大小** | ❌ **不能**（由事务大小定，与描述符数量无关） |
| IOMMU 页表 / IOTLB | **映射粒度** | ✅ 能（靠物理连续 + 大页） |

**用法**：要判断"某个优化能不能减少某个结构"，先问**那个结构是按哪一层的单元计数**，再看这个优化改变的是哪一层的单元。跳过这一步就会得出错误结论（例如"合并描述符能减少 outstanding 表项"——错的）。

**顺序管理：四个层次**

**① 描述符之间**——是要求**按序提交**还是**按序完成**？常见做法是乱序执行 + 按序完成报告（需要重排表）。

**② 传输内部**——一个传输切成的包要不要按序落地？批量数据通常不需要，**但有 fence 的地方需要**。

**③ 传输之间（依赖）**——最典型：

```
传输 A：把数据写进 buffer X
传输 B：从 buffer X 读出来发给对端
```

**B 不能在 A 的写"可见"之前开始**（注意是"可见"，不是"已发送"）。实现手段是**屏障（barrier）**：描述符流里插一个标记，"之前的所有传输必须完成，之后才能开始"。

**④ 内存模型的顺序**——**同一个引擎，不同目标内存的排序规则不同**：

| 目标 | 排序保证 |
|---|---|
| 设备本地内存 | 通常弱排序，需要显式 fence |
| 主机内存 | PCIe 有自己的规则（posted / non-posted、relaxed ordering 位） |
| 对端 GPU 内存 | 跨卡，**最弱** |

**⑤ 与一致性操作的顺序**——flush（写回脏数据）必须在**读之前**完成；invalidate（让对端 cache 失效）必须在**写之后**发出；**这两个操作本身也是异步的，它们自己的完成也要纳入定序**。这是最容易漏的一环。

**屏障的代价**：`barrier` 会把流水排空，**吃掉前面所有合并和乱序执行的收益**。所以屏障放得密，引擎的所有优化都白做——这也是驱动要尽量少插屏障的原因。
